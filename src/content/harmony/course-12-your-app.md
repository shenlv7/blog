### 本讲目标

用一套可执行的方法选出你的题目，把 12 讲的能力映射到它上面，切出 2 周能做完的 MVP 并排出迭代节奏。

做完你会看到：一张属于你的「能力 → 需要哪讲」映射表，和一个本周就能动手的第一版清单。

### 为什么这样设计

大多数人的 App 死在「想做的太多、做完的太少」。所以选题不看「能不能做」，看「你是不是每天都在被它烦」。每天重复的动作有三个好处：需求真实、你自己就是用户、验收标准天然清晰（你会不会真的用它）。

MVP 的切法是**只保留一条主链路**。判断标准是一句话：如果删掉这个功能，用户还能不能完成「打开 → 做一件事 → 得到反馈」？不能，就留；能，就砍到第二版。习惯打卡的主链路是：打开 → 看到今天要做什么 → 点一下 → 完成。所以「统计图表」「多设备同步」「社交排行」全都不在第一版里。

先把流程跑通，再让界面好看。顺序反了，你会花两周调一个最终被推翻的按钮。

### 跟着做

**1. 用三个问题筛题。** 这件事我一周做几次（少于 3 次就别做）？现在我用什么替代（如果微信备忘录就够，说明痛点不成立）？能不能一句话说清它给谁解决了什么？

**2. 填这张能力映射表。** 左列是你的 App 需要的功能，右列是对应讲次和要补的东西：

| 你的 App 需要 | 对应讲次 | 12 讲之外要补什么 |
| --- | --- | --- |
| 静态页面、版式 | 1、3 | — |
| 数据模型、列表 | 2、5 | — |
| 增删改、状态同步 | 4、10 | — |
| 多页面、详情、回传 | 6 | — |
| 本地存储 | 7 | 数据量大或要查询时换 `relationalStore`（SQL） |
| 联网拉数据 | 8 | 登录态、Token 刷新、HTTPS 证书校验 |
| 定时提醒、通知 | 9 | 服务端推送用 Push Kit，不是本地通知 |
| 打包上架 | 11 | 隐私合规、备案、资质审核 |
| 相机 / 定位 / 传感器 | — | `@kit.CameraKit`、`@kit.LocationKit`、`@kit.SensorServiceKit` + `user_grant` 权限（第 9 讲有模板） |
| 音视频播放录制 | — | `@kit.MediaKit`、`@kit.AVSessionKit` |
| 分享 / 拉起别的应用 | — | `@kit.AbilityKit` 的 Want、`@kit.ShareKit` |
| 支付 | — | `@kit.PaymentKit`，需企业资质 |
| 蓝牙 / 硬件 | — | `@kit.ConnectivityKit`（BLE）、`@kit.BackgroundTasksKit`（长时任务） |
| 图表 | — | Canvas 手绘，或引入开源图表库并注意其 API 兼容性 |

**3. 切 MVP。** 写下你的主链路（不超过 4 步），然后列出第一版只做的三件事。三件之外的，全部写进 `v2.md` 里，并且**这个文件在第一版跑通前不许打开**。

**4. 排迭代节奏。** 每周一个可运行版本，每版只加一块能力，顺序建议：能看（第 3 讲）→ 能点（第 4、5 讲）→ 能存（第 7 讲）→ 能跳（第 6 讲）→ 能联网（第 8 讲）→ 能提醒（第 9 讲）→ 能装（第 11 讲）。不要一次加两块，「哪块坏了」会变成猜谜。

**5. 代码组织。** 沿用本项目的分层，按你说的 App 换名字：

```text
ets/
├── entryability/EntryAbility.ets   // 只管窗口与全局初始化
├── model/                          // 纯数据结构 + 纯函数，可单测
├── store/                          // 持久化，一个 store 一个文件
├── service/                        // 网络、通知、硬件，只暴露 Promise API
├── view/                           // 可复用组件，不含业务逻辑
└── pages/                          // 页面，只做编排：取数据 → 给 view → 接回调
```

铁律：`pages/` 里不出现 `http`、不出现 `preferences`、不出现 `notificationManager`。出现的那天，就是重构信号。

**6. 三个不同体量的选题示例。**

**A. 单人工具类：记账本。** 一条记账、按月分类汇总、本地存储。所需讲次：1、2、3、4、5、6、7、11，**不需要**第 8、9 讲。要补：分类汇总的聚合逻辑（纯函数，好测）、CSV 导出（`@kit.CoreFileKit` 的 `fileIo`）、简单柱状图（Canvas）。体量：2–3 周能做到可上架，适合第一次独立发布。

**B. 有后端：健身打卡 + 教练点评。** 用户体系、训练计划、教练端点评、数据同步。所需讲次：全部 12 讲都用得上。要补：一个后端（任何语言都行）+ 已备案的 HTTPS 域名、登录态与 Token 刷新（Token 存 `Preferences`）、离线队列与冲突合并、服务端推送（Push Kit）、用户协议与隐私政策。体量：2–4 个月，建议先做「只有自己用的离线版」，跑通后再接后端。

**C. 有硬件交互：宠物喂食器控制。** BLE 配网、定时投喂、余粮告警。所需讲次：1–11。要补：`@kit.ConnectivityKit` 的 BLE 扫描/连接/读写特征值、自定义 GATT 协议（找硬件方要协议文档）、长时任务与 `ohos.permission.KEEP_BACKGROUND_RUNNING`、断连重连与心跳。体量：1–2 个月，难点不在 UI 而在协议和异常恢复，务必先做一个「能连上并读到一个字节」的最小闭环。

### 容易踩的坑

- **现象**：做了三周，一个功能都没完整跑通。**原因**：同时在做好几块，没有可运行的中间态。**改法**：砍到一条主链路，本周必须能装上并自己用一次。
- **现象**：越做越像别人的 App。**原因**：从「我想做个 App」出发，而不是从「我每天被什么烦」出发。**改法**：回到那三个筛选问题，答不上来就换题。
- **现象**：第一版就纠结配色和动效。**原因**：把「好看」当成了「完成」。**改法**：先用系统默认样式跑通，第 2 版再统一视觉。
- **现象**：功能加得越多，改一处坏三处。**原因**：业务逻辑写进了 `pages/`，没有 `service` 和纯函数层。**改法**：按第 5 步的分层重构，把网络、存储、算法都移出去。

### 自检

- 你能用一句话说清你的 App 给谁解决了什么问题，且这句话里没有形容词。
- 你的映射表里，「12 讲之外要补什么」那一列不是空的 —— 空说明你还没想清楚边界。
- 你的 MVP 主链路能画成 4 步以内，且每一步都能在第 12 讲之前的某讲里找到对应实现。
- 你有一个「本周能做完」的清单，且不超过 3 项。
- 你能指出你的工程里 `pages/` 目录下还有哪几行代码该搬到 `service/`。

### 本讲产出

一份你自己的 App 选题说明、一张能力映射表、一个两周 MVP 清单。

### 进阶挑战

30 分钟内：基于第 1 讲的工程，把 `bundleName`、`label`、图标换成你自己的 App；把主链路第一步的页面画成静态版（第 3 讲的水平即可）；在 README 里写下主链路的四步和本周的三件事。做完这一步，你就不再是「学鸿蒙的人」，而是「有一个在跑的鸿蒙项目的人」。
