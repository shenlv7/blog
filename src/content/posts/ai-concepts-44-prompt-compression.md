# AI核心概念(44)：Prompt Compression（提示压缩）——你以为在省钱，它却在 16 倍处开始编数字

> 「把 8K 的上下文压成 1K，成本降到八分之一，效果几乎不掉」——这类结论在论文里成立，在工程里翻车，原因不在论文，在你**怎么量压缩比**、以及**你以为失败长什么样**。
>
> 我这篇做了三段本机实验。第一段自己写 token 级剪枝（用字符级 bigram 的困惑度当「可预测性」，是 LLMLingua 里小模型打分的廉价代理），扫描压缩比看针句什么时候断；第二段拿真实 API 对照（deepseek-chat，token 数直接读 `usage.prompt_tokens`，不估算）；第三段量 question-aware 压缩的**per-query 开销**。
>
> 结论先放这里：**4x 名义压缩率下真实 token 只压到 2.18x，六种组合全答对；16x 名义压缩率（真实 11.2x）下六种组合全答错，而且没有一次回答「文档里没有这个信息」，全部编出一个数字。** 压缩的失败模式不是「性能下降」，是「静默改答案」——这比掉点可怕得多。

## 🎯 术语与出处对齐

- **prompt compression（提示压缩）**：把喂给模型的 prompt 在不改任务语义的前提下变短，省 token（=省成本、省 prefill）。分为**硬压缩**（删除原文 token，输出仍是可读原文）与**软压缩**（压成 embedding / 特殊 token 序列，人类不可读）。
- **硬压缩的起点：LLMLingua**（Jiang、Wu、Lin 等，Microsoft，*LLMLingua: Compressing Prompts for Accelerated Inference of Large Language Models*，arXiv:2310.05736，EMNLP 2023）。三件套：(a) **budget controller** 按段分配预算（instruction / demonstration / question 不等权重）；(b) 用一个**小语言模型**（GPT-2 small、LLaMA-7B 一类）算每个 token 的困惑度，**删掉「可预测」的低信息 token**，保留高困惑度 token；(c) **迭代压缩**处理分布漂移。它给的定位是「高压缩比下性能损失很小」。
- **question-aware 版本：LongLLMLingua**（arXiv:2310.06839，ACL 2024）。在 LLMLingua 上加了粗到细的**问题相关性**压缩、文档重排、**动态压缩比**，专门打「长上下文里答案在中间」的场景。NaturalQuestions 上报告的读数是：约 4 倍更少的 token 时，性能相对原始 prompt 最高 +17.1%（v1 摘要写的是 GPT-3.5-Turbo 上 up to 21.4%，同一组实验不同版本口径，我按两个数字都记）。
- **task-agnostic 的转折：LLMLingua-2**（Pan、Wu、Jiang 等，arXiv:2403.12968，ACL 2024 Findings）。它不再用因果 LM 逐个 token 打分（那要过一遍前向，慢），而是**从 GPT-4 蒸馏出标注数据**，训练 BERT 级 encoder 做 token 级二分类（保留/删除）。公开的读数是：压缩器本身比既有方法**快 3x–6x**，在 **2x–5x 压缩比**下端到端延迟加速 **1.6x–2.9x**。
- **为什么「task-agnostic」是一句工程话**：question-aware 意味着**每个新问题都要重新压一次**。这不是免费的操作（见下文第三段量出来的 3 倍差），而且压出来的 prompt 每问都不同，**前缀缓存直接失效**。

## 🔬 实验 1：token 级剪枝的断崖在哪

构造一份 85 行、约 2776 个字符级 token 的「机房巡检纪要」：大量同质干扰句（第 NN 机柜温度 X 度、风扇转速 Y 转……），里面埋两根针：

- **热针**：`代号K-7749的物料每台出厂成本是3,412元`——Q1 会问到它；
- **冷针**：`涂装车间的钝化剂单桶采购价是867元`——压缩时用的问题里**不含**它的任何关键词。

剪枝按预算保留得分最高的一批 token，两种打分：`ppl-only`（只有困惑度）与 `qa`（困惑度 + 整句与问题的字符重合加权）。

| 保留率 | 策略 | 金标数字 token（7749 / 3,412） | 冷针数字 token（867） | 针句 token 召回 |
|---|---|---|---|---|
| 0.25 | ppl-only | 2/2 | 1/1 | 100.0% |
| 0.25 | qa(Q1) | 2/2 | 1/1 | 100.0% |
| 0.25 | qa(Q2) | 2/2 | 1/1 | 100.0% |
| 0.125 | ppl-only | **1/2** | 1/1 | **41.9%** |
| 0.125 | qa(Q1) | 2/2 | 1/1 | 96.8% |
| 0.125 | qa(Q2) | 2/2 | 1/1 | 93.5% |
| 0.0625 | ppl-only | **0/2** | **0/1** | **6.5%** |
| 0.0625 | qa(Q1) | **0/2** | **0/1** | 54.8% |
| 0.0625 | qa(Q2) | **0/2** | **0/1** | 16.1% |

读三件事：

1. **8x（0.125）是 ppl-only 的断裂点**：金标数字只剩一半（丢的是 `3,412` 那个答案本身，留下的是罕见实体 `7749`），针句整体召回掉到 41.9%。同一档位 question-aware 还是 2/2、96.8%——**这就是 LongLLMLingua 那类方法真正赢的地方：中间档位**。
2. **question-aware 的收益有窗口，不是单调的**。到 16x（0.0625），qa(Q1) 的针句 token 召回还有 54.8%（说明它确实把预算往那句话里塞了），但**两个数字 token 全被删掉**。留住了句子的皮，丢掉了答案的肉。所以「问题相关」这条线只在还有足够预算时才管用。
3. **冷针是更诚实的对照组**：qa 压缩时看不见 Q2，它对 867 的保护就退化成一个接近随机保留的效果。任何「压缩后细节没丢」的结论，都要先问一句：**这个细节在压缩那一刻，是否已经被问题指到了？**

## 🏗️ 机制：为什么「可预测」可以删，以及为什么删到后面会连答案一起删

困惑度剪枝的前提很干净：**信息量 ≈ 意外程度**。在一份巡检纪要里，「第 37 机柜进气温度 24.1 度，风扇转速 2210 转，链路误码率为零」中，「机柜」「度」「转」几乎完全可预测（低 surprisal），而「24.1」「2210」是唯一信息（高 surprisal）。删前者，保留后者，理论上不丢信息——LLMLingua 就是这么把压缩比做上去的。

问题出在两处：

- **可预测 ≠ 可删除**。「的原因」「不是」这类高频 token 单个信息量很低，但它们是**语法骨架**。删到一定程度，留下的是一串高信息量碎片的「电报体」，人类还能猜，模型要花更多注意力去重建结构——这正好抵消了你省下的 prefill。
- **预算分配是全局的，重要性是局部的**。「哪个 token 是答案」这件事在压缩时**不可知**（除非问题已经指出来了，那就成了 question-aware 的循环依赖）。所以高压缩比下的删除不是「删无关信息」，而是**按统计规律随机擦除稀有事实**——稀有事实恰恰是答案。

这两点合起来解释了实验 2 那个反直觉的结果：**断崖之下的失败不是「答错得含糊」，是「答得很确定」。**

## 🧪 实验 2：真实 API —— 4x 全过，16x 全编

同一份文档，四种 prompt 变体，两个问题（Q1 问热针、Q2 问冷针），`temperature=0`，deepseek-chat，token 数读 API 返回的 `usage.prompt_tokens`：

| prompt 变体 | 本地剪枝保留率 | 真实 prompt_tokens | 相对全文 | Q1 命中 | Q2 命中 | API 给的答案 |
|---|---|---|---|---|---|---|
| 全文 | 1.0 | 2200 | 1.00x | ✅ | ✅ | 3412 / 867 |
| ppl 剪枝 | 0.25 | 1010 | 2.18x | ✅ | ✅ | 3412 / 867 |
| qa(Q1) 剪枝 | 0.25 | 1022 | 2.15x | ✅ | ✅ | 3412 / 867 |
| qa(Q2) 剪枝 | 0.25 | 1007 | 2.18x | ✅ | ✅ | 3412 / 867 |
| ppl 剪枝 | 0.0625 | **197** | **11.2x** | ❌ | ❌ | **1860** / **1860** |
| qa(Q1) 剪枝 | 0.0625 | 199 | 11.1x | ❌ | ❌ | **1805** / **1864** |
| qa(Q2) 剪枝 | 0.0625 | 199 | 11.1x | ❌ | ❌ | **1925** / **1925** |

四个必须写下来的读数：

1. **名义 4x，真实只有 2.18x。** 我按字符级 token 数的保留率定义压缩比（0.25），落到推理引擎真正计费的 token 上，2200 → 1010。原因很朴素：我的 tokenizer 是字符级的（一个汉字一个 token），真实 tokenizer 会把常见词合并。**所以凡是拿「字符压缩率」当成本收益写进方案的人，报出来的省钱都是虚高的**——论文里的 4x 是 token 级的。我后面所有结论只用真实 usage 数字。
2. **4x 档位看不出差别。** 三种策略、两个问题，六次全对，包括压缩时完全没被指到的冷针。**我原本预期 question-aware 在这里赢，实测是没有可测差异**——因为 25% 保留率本身不缺预算。这条要老实说：小规模、短文档上，question-aware 的复杂度很可能换不到任何东西。
3. **16x 档位：全军覆没，而且全部在编。** prompt 只剩 197 token，六个组合六次答错，**没有一次回答「文档里没有该信息」**，全部给出了一个看起来很像数字的答案。更值得警惕的是：`ppl@16x` 这个 prompt 下，Q1 和 Q2 两个不同问题返回的答案**一模一样（1860）**——说明模型不是「猜」，而是从残留噪声里抓住了一个数字并把它当作事实。压缩破坏文档后，模型的失败模式从「我不知道」切换成「这就是答案」。
4. **question-aware 在 16x 也救不回来**，这跟实验 1 完全对上：针对 Q1 压缩的版本，金标数字 token 存活 0/2，Q1 答了 1805。**保住零散词没用，语义结构没了就是没了。**
5. **延迟数字在这规模上没有信息量**：全文 2200 token 的 prefill 在 0.5–1.0 秒区间，压缩带来的差被噪声淹没。**「压缩 = 加速」只在 prompt 长到 prefill 真的成为瓶颈、且你确实保住了答案时才成立**——这也是我不会在这里报任何「快了多少倍」的原因（那需要固定引擎、固定并发、多轮重复测量）。

## 💻 可运行代码

完整脚本 `~/scripts/blog_daily/44-prompt-compression.py`（纯标准库，本机约 60 秒跑完，含 14 次真实 API 调用、合计 11668 prompt token）。核心两段：

```python
# 1) 用文档自身训一个字符级 bigram，算每个 token 的 surprisal（-= log2 p）
def surprisal(self, prev, tok):
    p1 = (self.uni[tok] + 0.05) / (self.N + 0.05 * self.V)          # 一元
    b  = (self.bi[(prev, tok)] + 0.05) / (self.uni[prev] + 0.05 * self.V) if prev else p1
    return -math.log2(0.7 * b + 0.3 * p1)                            # 回退插值

# 2) 按预算保留得分最高的 token；question 不为 None 即成 question-aware
for i, t in enumerate(tokens):
    s = lm.surprisal(tokens[i-1] if i else "", t)
    if question:                                   # LongLLMLingua 那一路的简化
        s += alpha * sent_overlap_with_question[t] # 整句与问题的字符重合度
        if t in set(question):
            s += qa_weight
    scores[i] = s
keep = set(sorted(range(len(tokens)), key=lambda i: -scores[i])[:int(ratio * len(tokens))])
```

关键不是复现论文（我的压缩器是 bigram，不是 GPT-2/BERT），而是**那段「扫描压缩比 × 策略 × 针句存活 × 真实 API 命中」的对照表**——它才是在自己数据上定压缩比的依据。

## 💡 带走三条

1. **压缩比按真实 tokenizer 计量。** 我的名义 4x 实测是 2.18x。用字符数、字数、或者「删了多少句」来算收益的，都会把省钱报高。
2. **压缩的失效形态是断崖 + 自信编造，不是缓慢掉点。** 所以生产里要监控的不是平均分，而是「该说不知道时有没有说」——在断崖之上，你的评估集永远看着很好。先在你自己语料上扫出这个断崖（实验 1 那张表的形态），再定压缩比，留一档余量。
3. **question-aware 的复杂度只在中间档位兑现，而且必须付 per-query 的代价。** 我的本机测量：纯困惑度压缩 16.5 ms/次（可复用于所有问题），question-aware 48.7 ms/次（每个新问题重压一遍，且压出来的 prompt 每问不同、前缀缓存失效）。这也是 LLMLingua-2 转向 task-agnostic、把压缩器蒸馏成 BERT 级 encoder 的工程动机——不是学术趣味。

**边界声明（必读）**：本文第一、三段是**本机离散模拟 + 本机 CPU 测量，不是 GPU 实测**；理解压缩用的是我自训的字符级 bigram，**不是论文里的 GPT-2 / LLaMA-7B**，量级与趋势可信、绝对值不可与论文对齐。第二段（实验 2）是**真实 API 调用**，token 数取自 API 返回的 `usage`，不是估算；但文档是我合成的（85 行同质句子），所以请把它读作「机制的对照实验」，而不是「某个模型在 NQ/LongBench 上的分数」。
