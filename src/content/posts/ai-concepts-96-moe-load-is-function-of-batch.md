> 看板上「专家负载均衡」四个字，容易被读成一个静态属性：路由器训练得好，负载就均衡。于是容量因子设在 1.25 就觉得稳了，反正「均衡」嘛。
> 但 batch=1 的请求里，256 个专家只有 8 个会被唤醒——那 8 个之间的负载不是「均衡的分布」，而是 8 个具体的数字，最大那个是平均值的 32 倍。
> 均衡从来不是路由器的属性，它是 (路由器, 批大小) 这一对的属性。

**读这篇要会**：MoE 的 top-k 路由（每个 token 只走 k 个专家）/ 变异系数 CV = 标准差÷均值 / roofline 里的「算术强度」——不是必须，但第 20 篇讲了专家坍缩的训练侧，这篇讲它在服务侧的后果。

## 🎯 先把「利用率」这个词拆开

MoE 省算力，省的是**每个 token 走过的参数**，不是**每个 token 要读过的权重**。这两件事在训练的大 batch 里几乎等价，在推理的小 batch 里差得很远。

一次解码步进来 B 个 token，每个 token 选 top-8 个专家。B=1 时被点名的专家是 8 个（可能有重复），占 256 个的 3.1%。剩下 96.9% 的专家权重这一步完全不动——听起来是好事，省显存带宽。问题在另一头：这里没有「同一份权重被多个 token 分摊」这回事。每个被唤醒的专家都只服务 1 个 token，它那 42MB 的 FFN 权重必须从 HBM 完整读一遍，然后做一个 M=1 的矩阵乘。

下面这批数字来自纯 numpy 模拟（不是 GPU 实测）：256 个路由专家、top-8、每个 batch size 跑 400 次取均值，路由 logits = 专家偏置 + N(0,1) 噪声。

| batch | 活跃专家（均匀路由） | 峰值/均值 | 覆盖率（解析式） |
|---|---|---|---|
| 1 | 8.0 / 256（3.1%） | 32.0 | 3.1% |
| 8 | 57.4 / 256（22.4%） | 9.4 | 22.4% |
| 32 | 163.3 / 256（63.8%） | 4.7 | 63.8% |
| 64 | 222.0 / 256（86.7%） | 3.4 | 86.9% |
| 256 | 255.9 / 256（100%） | 2.1 | 100% |

「峰值/均值 32」不是笔误。B=1 时 8 次投递落在 256 个格子里，均值 0.031，最热的格子拿到 1 个 token，就是均值的 32 倍。这个比值没有任何统计意义上的「坏」——它只是说明：小 batch 下拿负载均衡指标衡量路由器，测的是抽样噪声。

## 🔬 覆盖率只由批大小决定

均匀路由下，一个专家在 B 个 token 里一次都没被选中的概率是 `(1 - k/E)^B`，于是被唤醒的期望比例：

```
E_active / E = 1 - (1 - k/E)^B        # k=8, E=256
```

B=1 是 3.1%，B=32 是 63.8%，B=256 才接近 1。模拟值与解析式在 9 个 batch size 上逐项吻合，最大偏差 0.002（400 次蒙特卡洛的噪声量级）。这条式子值得记住的地方不是数字，而是它里面**没有路由器参数**：只要路由近似均匀，覆盖率就完全由 batch 决定，再怎么调门控网络也换不来更多被唤醒的专家。

这也解释了一个常见的误读——「我们的 MoE 在小流量下显存吃满、吞吐却上不去」。显存吃满是因为全部专家权重常驻；吞吐上不去是因为每个 token 只摊到 8 个专家、每个专家只摊到 1 个 token，GPU 在等 HBM，不在算。

## 🏗️ 偏置是常数项，加批量平均不掉

真实路由器不会均匀。训练完总有几十个专家被高频选中（它们在预训练里先拿到了更多 token，于是更会处理常见模式，于是更常被选中）。模拟里给每个专家加一个常数偏置 `b_e ~ N(0, σ²)`，其余不变：

| batch | 覆盖率（σ=0.7） | 峰值/均值 | 覆盖率（σ=1.2） | 峰值/均值 |
|---|---|---|---|---|
| 1 | 3.1% | 32.0 | 3.1% | 32.0 |
| 8 | 18.2% | 17.4 | 14.2% | 27.0 |
| 32 | 41.0% | 15.8 | 27.0% | 26.9 |
| 128 | 66.5% | 15.8 | 42.3% | 26.9 |
| 256 | 77.1% | 15.8 | 49.8% | 26.8 |

两件事同时发生。**覆盖率封顶了**：σ=0.7 时 batch 从 1 加到 256（256 倍），覆盖率只到 77.1%，剩下 59 个专家无论来多少 token 都不会被选中；σ=1.2 时更狠，一半专家是死的。**峰值/均值不再随 batch 下降**：从 B=32 起就锁在 15.8，涨多少批量都压不下去。

原因是噪声和偏置在统计上是两类东西。批量平均的是零均值噪声，`std(负载) ∝ 1/√B` 那套只对噪声成立；偏置是常数，它的贡献不随 B 缩小。当 B 大到噪声项可以忽略，负载分布就收敛到 softmax 后的偏置分布本身——CV 15.8 就是那个分布的 CV，跟 batch 无关。

工程上这是两个不同的账单，而且必须付一张：

1. **把容量因子设到峰值**（15.8 倍），最热的专家永远不溢出，代价是 94% 的专家算力常年空转，MoE 的算力优势全部吐回去；
2. **按均值设容量、溢出就丢 token**，那张 GPU 不空转了，但被丢的 token 不是随机的：它们集中在那几个热专家上，也就是「最常见的模式」。丢的是训练分布的主体。

这也正是 DeepSeek-V3 那套「无辅助损失负载均衡」要解决的问题：不靠一个加在损失里的均衡项去拧，而是给每个专家维护一个偏置，按上一批的实际负载动态加减（过载的减、闲置的加），只在选 top-k 时加进 logits、不进梯度。偏置成了控制量，覆盖率就不再由 batch 单方面决定。

## 💻 算一遍 B=1 的算术强度

以 DeepSeek-V3 的量级为例：d_model 7168、专家中间维 2048、fp8 权重，单个专家的 FFN 是 3×7168×2048 ≈ 4400 万参数（42 MiB）。B=1 时一个 token 唤醒 8 个专家：

- 权重流量：8 × 42 MiB ≈ **336 MiB**
- 计算量：8 × 2 × 7168 × 2048 ≈ **0.235 GFLOP**
- 算术强度：0.235e9 ÷ 352e6 ≈ **0.67 FLOP/byte**

按 H100 SXM 的规格（fp8 稠密 989 TFLOPS、HBM 3.35 TB/s），机器平衡点是 989e12 ÷ 3.35e12 ≈ 295 FLOP/byte。0.67 比它小两个多数量级，换算成算力利用率约 0.2%——这颗 GPU 这一秒几乎全在搬权重。EP=8 时每个被唤醒的专家落在不同卡上，单卡读自己那 42 MiB 大约 13µs；all-to-all 每个 token 只发 8×7168×1B = 56KB（每卡 7KB），付的是延迟，不是带宽。

所以「加批量」在 MoE 上的真实作用是：让同一份专家权重被更多 token 分摊。均匀路由下 batch 从 1 到 256，每个被唤醒的专家平均收到的 token 从 1 个涨到 8 个（2048 次投递 ÷ 256），算术强度从 0.67 抬到约 5.4 FLOP/byte——离 295 还差两个数量级，但每条读出来的权重多干了 8 倍的活，这就是吞吐曲线随批量上升的机制，而不是「GPU 更忙了」。

```python
# 96-moe-load-vs-batch.py 的核心（完整脚本见文末链接）
import numpy as np
E, K, TRIALS, BS = 256, 8, 400, [1, 2, 4, 8, 16, 32, 64, 128, 256]

def coverage(bias_sigma, seed=96):
    rng = np.random.default_rng(seed)
    bias = rng.normal(0, bias_sigma, E) if bias_sigma else np.zeros(E)
    for B in BS:
        act, peak = [], []
        for _ in range(TRIALS):
            logits = bias[None, :] + rng.normal(0, 1, (B, E))
            idx = np.argpartition(-logits, K, axis=1)[:, :K]   # 每个 token 的 top-8
            cnt = np.bincount(idx.ravel(), minlength=E)        # 每个专家收几个 token
            act.append((cnt > 0).mean())
            peak.append(cnt.max() / (cnt.mean() + 1e-12))
        print(f"B={B:>3}  激活 {np.mean(act):.3f}  峰值/均值 {np.mean(peak):.2f}")

for s in (0.0, 0.7, 1.2):
    print(f"-- bias sigma={s}"); coverage(s)
```

## 💡 落地清单

- **报 MoE 吞吐必须带 batch size**。脱离 batch 的「MoE 比稠密快 3 倍」没有意义：B=1 时它快是因为激活参数少，B=256 时它快是因为专家权重被摊薄，两种快来自不同的账本。
- **监控路由偏置，别只监控 aux loss**。训练侧的均衡损失可以很小，服务侧的峰值/均值照样是 16 倍——它们量的不是同一个东西。
- **小并发场景优先考虑「少而大」的专家或专家副本**。256 个专家在 batch=1 下等价于 8 个专家，剩下 248 个只贡献显存占用；同样显存摆 32 个专家、每个副本 2 份，热专家的排队长度会短得多。
- **容量因子按 p99 负载设，不要按均值**。按均值设必然丢 token，而丢的是最常见模式的那批；要么接受丢弃并监控丢弃率，要么把容量加到峰值并承认算力空转。
