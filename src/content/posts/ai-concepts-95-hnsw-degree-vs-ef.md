> 索引面板上，`m` 和 `ef_search` 并排摆在一起，像两个同类旋钮：一个说「每个点连几条边」，一个说「查询时看多少个候选」。文档补的那句「ef_search 越大召回越高」，于是被当成唯一的调法——把 ef 往上推，召回自然上去。
> 这两个数不在同一层。M 在建图那天就决定了图里有没有那条边；ef 决定你在已有的边上愿意走多远。边走不到的地方，多走没用。
> 1500 条向量上：M=4 的图把 ef 从 10 推到 512，距离计算从 91.6 次涨到 1322.3 次（14.4 倍），召回 0.710 → 0.997；而 M=16 只花 271.9 次就到 0.993。前者那个「高召回」已经花掉了穷举的 88%。

**读这篇要会**：余弦/内积距离与高维最近邻的含义 / 图上的贪心爬山（每次只往更近的邻居移动）/ 第 36 篇里 IVF 的「探针覆盖率」——不是必须，但那篇讲了另一种索引的同类上限。

## 🎯 数据集本身决定了实验能不能测出差异

如果最近邻距离和第十近邻距离差得很远，任何 ef≥16 的图都会直接给出 100%——那不是 HNSW 强，是题目太简单。这批数据把簇内散度（1.1–1.5）调到接近簇心间距（0.55），1500 条向量的 1-NN 平均距离 0.242、10-NN 平均距离 1.162，最近邻才真正不唯一，召回才有掉的余地。

50 个簇心撒在 64 维单位球上，每条向量从随机一个簇心出发、加上散度乘高斯噪声，再归一化。查询 400 条，取自「随机数据点 + 0.25 噪声」——模拟找相似，而不是查自己（查自己在 HNSW 里几乎总是命中，测不出东西）。

## 🔬 实验：全量距离矩阵当真值，四张图各扫一遍

真值不需要近似：1500×1500 全量两两距离一次算完（9MB），`argsort` 取精确 top-10。索引侧是自己写的标准 HNSW——层数按几何分布抽签、层 0 度数上限 2M、新点从最上层贪心下行、层内用 `efConstruction=64` 搜索、邻居按多样性启发式挑选、超限裁剪。唯一的改动是**在 `search_layer` 里数距离计算的次数**，每算一次向量距离加一。

用距离计算次数而不是墙钟时间做单位，是因为 HNSW 的耗时几乎全在这一项上，而墙钟会被 SIMD 批量化、缓存命中、机器负载吃掉——同一段代码在这台 3 核机器上跑两次能差 20%，距离计算次数是确定的。

## 📊 结果：两个旋钮的量级完全不同

召回（对齐精确 top-10，400 条查询取平均）：

| M（层0 实际度数） | ef=10 | ef=32 | ef=128 | ef=512 |
|---|---|---|---|---|
| 4（8） | 0.710 | 0.853 | 0.962 | 0.997 |
| 8（16） | 0.935 | 0.974 | 0.999 | 1.000 |
| 16（32） | 0.993 | 0.998 | 1.000 | 1.000 |
| 32（64） | 1.000 | 1.000 | 1.000 | 1.000 |

每查询实际执行的向量距离计算次数（全量穷举 = 1500）：

| M | ef=10 | ef=32 | ef=128 | ef=512 |
|---|---|---|---|---|
| 4 | 91.6 | 218.6 | 641.0 | 1322.3 |
| 8 | 161.4 | 393.6 | 997.4 | 1475.6 |
| 16 | 271.9 | 637.2 | 1275.8 | 1497.5 |
| 32 | 476.4 | 951.8 | 1437.5 | 1499.0 |

两张表要横着一起读。M=4/ef=128 花 641 次距离拿到 0.962；M=16/ef=10 花 271.9 次拿到 0.993——**便宜 2.4 倍，还准 3 个点**。M=4 想要 0.993 这一档，ef 得推到 400 以上（在 128 的 0.962 和 512 的 0.997 之间插值，约 470），距离计算落在 1.2k 上下，是 271.9 的四倍多。

## 🏗️ 机制：不是图断了，是路太窄

「HNSW 召回上不去，大概是图连通性出了问题」是常见解释，这批数据里它不成立：M=4 到 M=32 四张图，层 0 的连通块都是 1，没有一个孤立点。图是通的，召回照样掉 28 个点。

真正的约束在每一步的**视野宽度**。贪心搜索每次弹出一个候选点，只能读它的邻接表：M=4 时层 0 平均 8 条边，站在簇边界时这 8 个邻居可能全在本簇里，正确簇的点压根没进候选堆。`search_layer` 的终止条件是「候选堆顶比结果集里最差的还差」——候选堆里没有正确簇，条件立刻成立，搜索就地收工。ef 只决定结果集的容量，容量再大，池子里没有那块点，也捞不出来。

所以 M=4 的曲线在 0.997 封顶：ef=512 时它已经算了 1322.3 次距离，是穷举的 88%，比 M=8 在 ef=512 的 1.000 还差 0.3 个点。再往上，所有曲线都会收敛到 1475–1499——ef 推进到 N 附近时，索引退化成暴力扫描加一层壳。

三个量可以互相验：

- **层数上界** $L_{\max} = \lfloor \log_M N \rfloor$。N=1500、M=4/8/16/32 依次是 ⌊5.29⌋、⌊3.52⌋、⌊2.63⌋、⌊2.11⌋ = 5、3、2、2，与实测最高层 5/3/2/2 逐项对上。
- **层分布** $P(l) \propto \exp(-l/\lambda)$，$\lambda = 1/\ln M$——M 越大，层数越浅，上层能做「粗路由」的层级越少。
- **单查询距离计算** ≈ $ef \cdot M_0 + L_{\max}\cdot M$，其中 $M_0 = 2M$。M=16、ef=10 估 352 次，实测 271.9（提前终止省掉的那部分）；四组比值落在 0.68–0.92。

建图的账单和查询正好相反。M=4/8/16/32 的构建耗时是 4.8s / 14.0s / 45.3s / 160.7s，M 从 4 到 32（8 倍）时间涨 33.5 倍——接近 M²：每插一个点都要在 `efConstruction` 个候选里做一遍多样性筛选，候选本身又由 M 决定。

## 💻 核心逻辑

```python
class HNSW:
    def __init__(self, M, efC):
        self.M, self.M0, self.efC = M, 2 * M, efC      # 层 0 的度数上限是 2M
        self.mL = 1.0 / np.log(M)                      # 层分布 P(l) ∝ exp(-l/λ)
        self.graph, self.entry, self.max_level, self.dc = [], None, -1, 0

    def search_layer(self, row, eps, ef, layer):
        visited = set(eps)
        res  = [(-row[e], e) for e in eps]; heapq.heapify(res)    # 结果集，按距离
        cand = [( row[e], e) for e in eps]; heapq.heapify(cand)   # 候选堆，近的优先
        while cand:
            d, c = heapq.heappop(cand)
            if len(res) >= ef and d > -res[0][0]:
                break                                  # 候选比结果集最差的还差 → 收工
            for e in self.graph[c][layer]:
                if e in visited: continue
                visited.add(e); self.dc += 1           # 只数真正算过的距离
                dd = row[e]
                if len(res) < ef or dd < -res[0][0]:
                    heapq.heappush(cand, (dd, e)); heapq.heappush(res, (-dd, e))
                    if len(res) > ef: heapq.heappop(res)
        return sorted((-d, e) for d, e in res)

    def insert(self, i):
        row = DM[i].tolist()
        lvl = int(-np.log(rng.random()) * self.mL)     # 层数抽签
        self.graph.append([[] for _ in range(lvl + 1)])
        if self.entry is None:
            self.entry, self.max_level = i, lvl; return
        ep = [self.entry]
        for layer in range(self.max_level, lvl, -1):   # 上层每层只走 1 跳，找入口
            ep = [self.search_layer(row, ep, 1, layer)[0][1]]
        for layer in range(min(lvl, self.max_level), -1, -1):
            W  = self.search_layer(row, ep, self.efC, layer)
            cap = self.M0 if layer == 0 else self.M
            nb = self.select(W, cap)                   # 多样性启发式，不是取最近的 M 个
            self.graph[i][layer] = nb
            for j in nb:                               # 双向连边，超限就裁
                self.graph[j][layer].append(i)
                self.shrink(j, layer, cap)
            ep = [e for _, e in W]
```

`select` 里那句判据是整套东西的关键：候选点 $\text{cand}$ 只有在「到查询的距离比它到已选邻居的距离都近」时才入选，否则跳过。只取最近的 M 个会让所有邻居挤在同一个方向上，图退化成一堆局部小团；多样性挑选用一部分近邻名额换「往别的方向也有边」。完整脚本（数据生成、连通块统计、扫参网格）：[demos/95-hnsw-degree-ceiling.py](https://github.com/shenlv7/blog/blob/main/demos/95-hnsw-degree-ceiling.py)。

## 💡 调参顺序反过来

1. **先把 ef 钉在 10–16，扫 M。** 这一档 ef 便宜，跑一遍就知道你的数据在「度数够不够」这一层卡在哪；M=16 在 ef=10 已经 0.993 的数据，把 ef 推到 512 是在给已经不存在的错误买保险。
2. **再用 ef 补最后一两个点，不要用 ef 补二十个点。** M=4 从 0.710 爬到 0.962 要 7 倍算力；同样 7 倍算力花在 M 上（4→16，建图贵 9.4 倍但查询只贵 3 倍）能直接到 0.993。
3. **监控「每查询距离计算 / N」而不是只看 recall。** 这个比值逼近 1，说明索引在一次查询里几乎扫了全库——要么 ef 太大，要么图太稀。它比 P99 延迟更早报警，且不受机器负载干扰。
4. **M=32 的边际收益要打折看。** 层 0 度数 64，ef=10 时花 476 次距离（M=16 的 1.75 倍）只换 0.7 个点，建图贵 3.5 倍，索引里层 0 的边数也翻倍。
5. **recall@10 = 1.000 不等于检索对了。** 它衡量的是「和精确 top-10 的重合度」，衡量不了 embedding 本身能不能把正确答案放在近处——那是第 37、65 篇的事。

**边界**：数据是 1500 条、64 维的合成簇，比生产上 768–1024 维的真实 embedding 容易，簇结构也更规整，绝对值会整体偏高；比的是距离计算次数而不是墙钟时间，真实库把邻居批次向量化、走 SIMD，常数项能差一个量级，但 M 与 ef 的相对位置不变；这里没有删除和更新，而 HNSW 的 tombstone 删除会额外损失召回，那部分是另一笔账。
