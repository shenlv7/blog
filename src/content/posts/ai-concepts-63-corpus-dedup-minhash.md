> 我一直在调 LSH 的 `b×r`，想让召回率高一点。
> 八组配置都试完了，完全相同的副本召回一直是 1.000。
> 也就是说：捞不回来的那些文档，从一开始就没被算成「相似」。

**读这篇要会**：集合与 Jaccard 的定义 / 哈希函数的最小值性质（为什么 min 能估计集合重合）/ 基本的 numpy 向量化。不需要 GPU，不需要训练任何模型，全部在一台 3 核 ARM 机器上跑完。

## 🎯 我要去重的是什么，为什么它值钱

预训练语料里最常见的问题不是「有脏数据」，而是**同一篇文章出现了几十次**：转载、镜像、加个免责声明的翻版。模型在这些重复上多训练几十遍，等于给这部分数据偷偷调高了学习率 —— 小模型上表现为分布偏移，大模型上表现为「你说上半句它就开始背」。

工业界的做法是 MinHash + LSH：把每篇文档压成一个短签名，再用分带把「签名某几段相同」的文档扔进同一个桶，只比较桶内的对。这个思路公式很干净，但**「召回率多少」这个数字从来没人给我**。

所以这次我不问「LSH 怎么配」，我先把答案造出来：250 个源文档，每个源生成 7 个编辑强度不同的变体（0%、5%、10%、20%、30%、45%、60% 的词被替换/删除/插入），一共 2000 篇。谁跟谁同源是已知的，这就是 oracle。然后看 LSH 能捞回多少。

## 🔬 三个公式，和它们各自漏掉的东西

**第一层：把文档变成集合。** 取 5 个连续 token 构成一个 shingle，一篇文档就是一个 shingle 集合 `A`。两篇文档的相似度用 Jaccard：

$$J(A,B) = \frac{|A \cap B|}{|A \cup B|}$$

**第二层：MinHash。** 随机取一个置换 $\pi$，定义 $h_\pi(A) = \min_{x \in A} \pi(x)$。可以证明

$$P\left[h_\pi(A) = h_\pi(B)\right] = J(A,B)$$

也就是说，抽 128 个随机置换，数一数有多少个置换上两篇文档的最小值相同，再除以 128，就得到 Jaccard 的无偏估计。实测 128 个置换的绝对误差均值 0.0043，p95 0.0230 —— 这一层是可靠的。

**第三层：banding。** 把 128 维签名切成 `b` 段、每段 `r` 行（`b×r ≤ 128`）。只要**任意一段**完全相同，两篇文档就进同一个桶、成为候选对。命中的概率是

$$P(s) = 1 - \left(1 - s^{r}\right)^{b}$$

令 $P(s)=1/2$ 解出阈值 $s^* \approx (1/b)^{1/r}$。教科书到此为止：选个阈值，收工。

问题在于，$P(s)$ 描述的是「**在 Jaccard 等于 s 的前提下**，LSH 能不能找到」。它完全没说：你要找的那批文档，Jaccard 到底是多少。

## 🏗️ 先看后两步：分数本身有多高

实验 [1]：同一个源文档和它的变体，只换 shingle 长度，看 Jaccard 怎么变（12 万条计算，取 100 个源的均值）：

| 编辑比例 | 3-gram | 5-gram | 8-gram |
|---|---|---|---|
| 0% | 1.000 | 1.000 | 1.000 |
| 5% | 0.779 | 0.659 | 0.520 |
| 10% | 0.606 | 0.443 | 0.290 |
| 20% | 0.400 | 0.234 | 0.115 |
| 30% | 0.282 | 0.138 | 0.052 |
| 45% | 0.166 | 0.060 | 0.015 |
| 60% | 0.097 | 0.025 | 0.004 |

两个事实立刻跳出来：

**一、编辑 10% 的文档，5-gram Jaccard 只有 0.443。** 换掉十分之一的词，人眼看还是同一篇文章，Jaccard 已经掉到「可疑相似」区间。编辑 30% 只剩 0.138，比很多无关文档之间的「模板相似」还低。所谓「Jaccard > 0.8 就算重复」是个约定，不是物理定律 —— 同一对文档，用 3-gram 是 0.606，用 8-gram 是 0.290。**阈值不能脱离 shingle 长度单独讨论**，这句话在几乎所有去重配置里都被省略了。

**二、shingle 越长，越容易把近重复判成不重复。** 8-gram 在 5% 编辑时就掉到 0.52 —— 因为 8 个词的窗口里只要有一个词被改，这个 shingle 就整个消失。3-gram 抗编辑强，代价是无关文档也容易撞。

## 💻 跑起来：MinHash 与 banding 的核心

完整脚本（含语料生成、oracle、八组配置遍历、削模板前后对比）在仓库：[demos/63-corpus-dedup-minhash.py](https://github.com/shenlv7/blog/blob/main/demos/63-corpus-dedup-minhash.py)。

核心就三段。**签名**：把每个置换写成一次线性哈希 `(a·h + b) mod p`，用 numpy 一次算完整篇文档的所有置换，取行最小值：

```python
M31 = 2147483647                # 梅森素数：a*hv 不会溢出 int64

def hash_shingles(sh, k=5):
    return np.unique(np.fromiter(
        (zlib.crc32(s.encode()) % M31 for s in sh), dtype=np.int64))

def minhash_signatures(hashes_list, num_perm, a, b):
    sig = np.empty((len(hashes_list), num_perm), dtype=np.int64)
    for i, H in enumerate(hashes_list):
        if H.size == 0:
            sig[i] = M31 - 1
            continue
        # (num_perm, m)：每行一个置换，取该行最小值
        sig[i] = ((a[:, None] * H[None, :] + b[:, None]) % M31).min(axis=1)
    return sig
```

**分带**：把第 j 段的 r 行字节序列当桶键 —— 注意这里没有再做哈希，直接 `tobytes()`，避免引入额外碰撞：

```python
def lsh_pairs(sig, bands, rows):
    buckets = defaultdict(list)
    for j in range(bands):
        seg = sig[:, j * rows:(j + 1) * rows]
        for idx in range(sig.shape[0]):
            buckets[seg[idx].tobytes()].append(idx)
    pairs = set()
    for bucket in buckets.values():
        if len(bucket) > 1:
            pairs.update(itertools.combinations(bucket, 2))
    return pairs
```

2000 篇 × 128 置换 = 0.97 秒，单核 2060 篇/秒，签名矩阵 2.05 MB。按这个速率线性外推，1e6 篇（假设文档长度不变）大约 8 分钟单核；签名存成 uint32 是 512 MB。真实文档比我的 159 词长 4-6 倍，时间也要乘上去 —— **这是外推，不是实测**。

## 📊 八组 b×r，召回爬不上去

实验 [3]，128 个置换，同一份签名：

| b×r | 阈值 | 候选对 | 占全量 | 召回 | 副本召回 | 精确率 |
|---|---|---|---|---|---|---|
| 8×16 | 0.878 | 254 | 0.01% | 0.036 | 1.000 | 1.000 |
| 16×8 | 0.707 | 514 | 0.03% | 0.073 | 1.000 | 1.000 |
| 16×4 | 0.500 | 1,051 | 0.05% | 0.150 | 1.000 | 1.000 |
| 32×4 | 0.420 | 1,272 | 0.06% | 0.182 | 1.000 | 1.000 |
| 16×2 | 0.250 | 14,509 | 0.73% | 0.311 | 1.000 | 0.150 |
| 32×2 | 0.177 | 22,495 | 1.13% | 0.383 | 1.000 | 0.119 |
| 48×2 | 0.144 | 26,456 | 1.32% | 0.429 | 1.000 | 0.114 |
| 64×2 | 0.125 | 102,207 | 5.11% | 0.463 | 1.000 | 0.032 |

三列数字连起来读：

**「副本召回」这一列全部是 1.000。** 我给完全相同的副本单独算了一个召回：八组配置无一失手。LSH 本身没有漏人 —— 它该找到的全找到了。

**召回从 0.036 爬到 0.463，靠的是把阈值一路压到 0.125。** 而阈值压低的代价立刻出现在最后两列：候选对从 254 涨到 102,207（403 倍），精确率从 1.000 掉到 0.032。也就是说，你付出 99.9% 的候选对是假的，才换回 4 个多百分点的召回。

原因在实验 [1] 那张表里：我的变体有三分之二落在 Jaccard 0.05–0.25 区间，而那个区间里**任何**阈值都会同时圈进大量模板相似的无辜文档。召回不是被 LSH 卡住的，是被「5-gram Jaccard 这个相似度本身」卡住的。

逐档看更清楚（固定 b=32, r=4，阈值≈0.42）：

| 编辑比例 | 真 Jaccard | 召回 | 签名估计 |
|---|---|---|---|
| 0% | 1.000 | 1.000 | 1.000 |
| 5% | 0.656 | 1.000 | 0.656 |
| 10% | 0.447 | 0.748 | 0.451 |
| 20% | 0.232 | 0.092 | 0.238 |
| 30% | 0.133 | 0.008 | 0.138 |
| 45% | 0.059 | 0.000 | 0.063 |
| 60% | 0.027 | 0.000 | 0.028 |

「签名估计」和「真 Jaccard」几乎逐行重合（最大差 0.005）—— MinHash 估得准。所以 20% 编辑那一档召回只有 9.2%，不是因为签名不准，也不是因为分带太严，而是那批文档的 Jaccard 真的只有 0.232，而阈值是 0.42。**它本来就不该被 5-gram 判成近重复。**

## 💡 假阳性从哪来：模板

我给 200 个源文档加了一段 24 词的共享页脚（「all rights reserved this document is provided as is…」这类）。24 个词在 5-gram 下贡献 20 个 shingle，而一篇正文约 135 个 —— 于是任意两篇带页脚的文档，光靠页脚就有

$$J \approx \frac{2 \times 20}{155 + 155 - 20} \approx 0.14$$

的真实 Jaccard。这个数刚好卡在 0.125–0.15 之间：**阈值 0.42 及以上的四组配置一对都没多捞**（跨源假阳性 0 对），阈值降到 0.14 以下的四组则被页脚淹没。实验 [5] 的候选对里，跨源对全部来自「两端都带页脚」的文档。

这就是为什么真实语料去重里，第一件事不是调 LSH，而是**先削掉模板**：版权头、导航栏、免责声明、爬虫抓下来的「上一篇/下一篇」。

实验 [6] 我按文档频率做了一遍：统计每个 shingle 出现在多少篇文档里，出现率 > 5% 的直接丢弃。结果只砍掉 **24 个 shingle —— 占全部 176,523 个的 0.01%**，每篇文档的 shingle 数从 154.8 降到 144.8（少 6.5%）。

同一套签名跑 64×2：

| 指标 | 削模板前 | 削模板后 | 变化 |
|---|---|---|---|
| 候选对 | 102,207 | 3,103 | −97.0% |
| 召回 | 0.463 | 0.439 | −0.024 |
| 精确率 | 0.032 | 0.989 | ×31 |

**删掉 0.01% 的 shingle，消掉 97% 的候选对，召回只掉 2.4 个百分点。** 而这个过程是完全自动的 —— 不需要知道模板长什么样，只需要知道「到处都是的东西不是内容」。

## 🚧 我第一版为什么是废的

第一版我只做了一件事：把 `b×r` 定成 16×8，阈值 0.707，然后跑出「候选对 514，精确率 1.000」，报告写着「去重完成，识别出 X% 的重复」。三个错误叠在一起：

**第一，精确率 1.000 让我很安心，可它在这份语料上是必然的。** 我的文档是伪词随机生成的，不同源的文档之间天然 Jaccard ≈ 0.001，除了我特意塞进去的页脚，根本没有「无关但相似」的对。**在干净合成语料上测出来的精确率，等于在测我的语料生成器。** 真实语料里，同一领域的文章、同一份 API 文档的不同章节、同一首歌的不同歌词页，Jaccard 常年 0.1–0.3。

**第二，我把「召回」算错了。** 我拿 `候选对 / 同源对` 当作召回，但同源对里有一半是 45%/60% 编辑的变体 —— 那批文档连人都不一定认得出是同一篇（在这个实验里是我手工指定的 oracle）。把它们的漏检算成 LSH 的失败，等于要求一个 5-gram 相似度去完成语义判断。

**第三、我调参的目标本身是错的。** 我在优化「召回」，可真正决定语料质量的是「**留下来的是什么**」。0.463 的召回里，抓到的每一对至少共享 42% 的 5-gram，是确定重复；漏掉的那 54 对里有大量「改了 30% 词的同源文档」—— 该不该删是标注问题，不是算法问题。

改对之后我才明白顺序：**先看相似度分布（实验 [1]）→ 再定阈值 → 再选 b×r → 最后才做签名和分带**。我第一版是从最后一步往前做的。

## 💭 这篇不能证明什么

- **不是海量真实语料的实测**。2000 篇、伪词、受控编辑强度。真实网页语料的长度分布、语言混杂、模板密度都不一样，绝对数值不可迁移；能迁移的是**结构与量级**：召回被相似度函数封顶、低阈值换来候选爆炸、模板先削。
- **没有语义去重**。MinHash 只认字面共享。同一件事换句子重写的「语义重复」，这篇一个都抓不到 —— 那是 embedding 聚类（SemDeDup）的活，代价是每篇一次前向。
- **没测去重对训练效果的影响**。这篇的终点是「候选对集合」，不是「loss 降了多少」或「重复率从 X 降到 Y」。去重删多少算合适，需要下游指标回答，我这里没有。
- **1e6 篇的耗时是外推**（2060 篇/秒 × 文档长度折算），不是实跑。分带那一步我用了 Python 循环建桶，真实规模必须换掉，实际吞吐会更高。
- **「同源」的定义是我定的**：同一个源 + 给定编辑强度。真实世界里「重复」有争议（同一新闻的通稿算不算？引用了同一段产品说明算不算？），这篇用 oracle 绕过了争议，也就没回答它。

## 🎬 一句话收尾

调 LSH 参数是在调「找到的概率」，可去重的成败取决于「值不值得找」。八组配置里，完全相同的副本召回恒等于 1.000 —— 这说明 LSH 从来不是瓶颈；真正卡住你的是 5-gram 对「改写多少」的敏感度，和那些到处都是的模板文本。先削模板，再看分数分布，最后才轮得到 `b` 和 `r`。
