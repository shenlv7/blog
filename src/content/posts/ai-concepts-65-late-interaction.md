> 双塔检索只算一次点积，这是因为它在编码时就把 32 个 token 平均成了一个点。
> 我把两篇文档做成只差一个专名 —— 相关的那篇反而排在干扰项后面：0.8355 对 0.8546。
> MaxSim 不动编码，只在打分时让每个查询词各自去找落点，间距就翻正了。

**读这篇要会**：余弦相似度与双塔（bi-encoder）检索的基本流程 / 矩阵乘法的复杂度怎么数 / 知道 `top-k` 召回是什么。不需要训练模型，不需要 GPU，numpy 单机 13 秒跑完。

## 🎯 双塔省掉的那一步，正是"词和词的比对"

主流向量检索是这么干的：文档进编码器，输出 1 个向量存起来；查询进同一个编码器，输出 1 个向量；检索时算一次余弦，取 top-k。索引里每篇文档只占 768 个浮点数，一次查询就是一次矩阵-向量乘，900 万篇文档在 CPU 上也能压到几十毫秒。工程上这是唯一能规模化的方案。

代价写在编码那一步里：**32 个 token 的信息被压进一个向量，压法是加权平均**。平均是个线性算子，它把"这篇文档提到了 X"这个事实，摊薄成 1/32 的权重，然后和其余 31 个词的成分混在一起。检索时那一次点积，比的是两份"平均后的词分布"有多像，不是"查询要的那个词在不在文档里"。

平时这不致命：如果查询和文档都在讲同一个话题，平均后的向量确实更像。真正失效的场景是**同领域里的细粒度区分** —— 一批文档全在讲 Python 性能，你要找的是提到 GIL 的那篇。话题成分在两边完全重叠，唯一的差别是一个专名，而它只值 1/32。

晚期交互（late interaction）不改编码器，只改打分：文档不再压成一个向量，每个 token 的向量都留着；打分时对每个查询 token，去文档的所有 token 里找最相似的那一个。

$$\text{MaxSim}(q,d)=\frac{1}{|q|}\sum_{t\in q}\ \max_{j\in d}\ q_t^\top d_j$$

而双塔的分数是

$$\text{score}(q,d)=\frac{\bar q^\top \bar d}{\|\bar q\|\,\|\bar d\|},\qquad \bar q=\frac{1}{|q|}\sum_t q_t,\quad \bar d=\frac{1}{|d|}\sum_j d_j$$

展开 $\bar q^\top\bar d$ 就能看出两者的差别：双塔的分子是 $|q||d|$ 个词对相似度的**平均**，高频背景词天然占大头；MaxSim 是每个查询词各自取**最大值**再平均，一个查询词只要在文档里找到一个高相似度的落点，就拿到满分，剩下 31 个背景词不参与扣分。

## 🔬 装置：让两篇文档只差一个词

要证明上面那段话，得把其他所有变量按住。合成空间，$D=128$：

- 词表 3000 个常见词、400 个专名，随机单位向量，词与词平均余弦 0.063（真实嵌入空间里不相关的词也不是精确正交的）。
- **所有文档共享同一组 29 个背景词**，模拟同领域语料。文档之间唯一的差别是第 30 个 token：每篇提到一个自己的专名，另有 2 个随机干扰专名。
- 相关文档的条件只有一个：它提到的那 1 个专名，正好是查询要找的。目标信号在文档里占 **1/32** 的权重，长度、词表分布、背景全部对齐。
- 查询 12 个 token：11 个背景词 + 1 个目标专名。真实提问也是这样，一整句话里只有一个词是关键。
- 4000 篇文档、150 条查询，每条查询恰好 2 篇正例。

这不是 BEIR 或 MS MARCO 上的实测，是合成空间里的单变量对照：把"一个词占多少权重"这件事单独拎出来看。真实的强基线（训练过的双塔）在话题级检索上并不弱，两者的差距只在细粒度词汇匹配上拉开 —— 这也是为什么这个装置要专门制造"背景完全重叠、只差一个专名"的条件。

打分函数是这三种：

```python
doc_mean = norm(docs.mean(1))              # A 均值池化：压成一个向量
doc_max  = norm(docs.max(1))               # B 逐维最大池化：另一个单向量做法

def maxsim(qi):                            # C 晚期交互：每个查询 token 各自找落点
    return (qrys[qi] @ flat.T).reshape(12, N_DOC, 32).max(2).mean(0)

def two_stage(qi, k=50):                   # D 单向量取 top-50，再用 MaxSim 重排
    cand = np.argsort(-(q_mean[qi] @ doc_mean.T))[:k]
    s = np.full(N_DOC, -1e9, dtype=np.float32)
    s[cand] = maxsim(qi)[cand]
    return s
```

## 💻 实测输出

```
docs=4000 tok/doc=32 queries=150，每条查询平均正例 1.94 篇

方法                          R@1   R@10    MRR  ms/query
A 单向量·均值池化                0.047  0.220  0.113       1.2
B 单向量·逐维max               0.007  0.013  0.012       1.1
C MaxSim(晚期交互)            1.000  1.000  1.000      33.6
D 两段式 top50→MaxSim        0.447  0.447  0.447      34.3

两段式上限：单向量 top-50 里正例覆盖率 = 0.280
存储：单向量 256 B(fp16)/篇 vs 晚期交互 4096 B(int8)/篇 = 32 倍；全库 1.0 MB vs 16 MB
A 均值池化: 相关 0.8355 / 最强非相关 0.8546 → 间距 -0.0192
C MaxSim: 相关 1.0001 / 最强非相关 0.9610 → 间距 +0.0391
```

逐维最大池化（B）几乎全错，值得单独说一句：对每个维度取所有 token 的最大值，等价于**伪造出一个不存在的词** —— 它的某一维来自第 3 个 token，另一维来自第 27 个。这个假词和任何真实查询词都不像，所以它连 R@10 都只有 0.013。单向量方案里能用的池化只有均值（或加权均值），而均值恰好就是"摊薄"。

## 📉 间距为负，不是排序不好，是排序反了

同一批数据上算两组分差：相关文档的平均分，对比每条查询里"最相似的那篇非相关文档"的平均分。

- 均值池化：相关 0.8355，最强干扰 0.8546，间距 **−0.0192**。也就是说干扰项系统性地压住了正确答案，不是随机抖动 —— 因为 1/32 的信号加进均值后，和"背景词恰好凑成一个更像查询平均向量的组合"分不开，而后者自由度更大：31 个背景词的抖动比 1 个专名值钱。
- MaxSim：相关 1.0001，最强干扰 0.9610，间距 **+0.0391**。相关文档的目标 token 与查询的目标 token 是同一个向量，$\max_j$ 必然取到 1.0；干扰文档的这一项平均只有 0.33（噪声里挑最大值，长尾能到 0.45），乘上 1/12 的平均权重，正好被压到 0.96。

两个间距加起来只有 0.058 宽 —— 这也说明为什么必须在 $D=128$、32 token 这个尺度上才看得见：向量维度一高、文档一长，1/32 会变成 1/300，均值池化的间距会进一步趋近 0。

## 💰 账单：32 倍存储、28 倍延迟，还有一张天花板

- **存储**：单向量 128 维 fp16 = 256 B/篇；每 token 128 维 int8 = 4096 B/篇，32 倍。真实规模的数字更难看：ColBERT 原始的 MS MARCO 索引是 **154 GiB**，ColBERTv2（NAACL 2022）用残差压缩做到 1~2 bit/维，压到 **16 / 25 GiB**，压缩比 6–10 倍 —— 而同样 900 万条 passage 的单向量索引（768 维 float32）本来只要 ~25 GiB。也就是说压缩之后的晚期交互，才勉强和未压缩的单向量打平。
- **延迟**：本机暴力打分 33.6 ms vs 1.2 ms，28 倍。这 33.6 ms 是 4000 篇 × 32 token × 12 个查询 token 全算一遍。工程上没人这么用 —— PLAID 一类引擎先用质心把候选剪到几千个再算 MaxSim，剪枝就是这篇的第二种做法（D）。
- **两段式的天花板**：D 的 R@1 = 0.447，而单向量 top-50 池内的正例覆盖率是 0.280。0.447 就是"至少一篇正例进了池子"的比例 —— 池子里没有的文档，MaxSim 再准也捞不回来。注意 D 的 R@1 和 R@10 都是 0.447：正例一旦进了池子，MaxSim 就把它排到第 1 位，重排阶段本身零损失，全部损失都发生在召回阶段。这是两段式架构的通用形状，和[重排序那篇](/blog/posts/ai-concepts-37-reranking/)（R@1 被池内命中率锁死）是同一个约束。

## 🔧 什么时候值得为每个 token 付 32 倍

判据不是"晚期交互更好"，而是**你的查询里有没有一个词，是文档必须字面提过的**。

值得上：

- 专名、型号、错误码、函数名、法条编号 —— 查询的关键是一个稀有 token，同领域文档的背景高度重叠。
- 法规、医疗、运维知识库：漏检一篇的代价远大于多花 30 ms。
- 需要给出证据片段：token 级相似度天然带"命中了文档里哪几个词"，可解释性白送。

不值得上：

- 话题级检索、宽泛问答。训练过的双塔在这个任务上很强，差的那点 Recall 用 BM25 混合就能补一部分。
- 索引规模在千万级以上、延迟预算几十毫秒。除非先做好候选剪枝，否则存储和延迟都撑不住。
- 文档很长（几千 token）。目标词的权重会掉到 1/1000 以下，均值池化彻底失效 —— 但也意味着你得先把长文档切短，那是分块的问题，不是打分函数的问题。

一条更省钱的中间路线：**只在重排阶段用 MaxSim**。索引继续用单向量，检索出 top-50~100 候选，对这批候选现算 token 向量再 MaxSim。存储不涨（候选是现算的），延迟多一次编码，代价是 R@1 被召回池的覆盖率写死 —— 本次实验里这个上限是 0.447，而不是 1.000。
