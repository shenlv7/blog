> 检索命中率 1.000，答案命中率 0.908。
> 差的这 9.2%，不是检索器弱，是切块时句号没落在你想要的位置。
> 同时开着的两个指标——「top-5 里有没有块提到这个词」和「top-5 里有没有块带着完整答案」——只差一个词，差出 55 条查询。

读这篇要会：TF-IDF 与余弦相似度（把文本变成稀疏向量、算夹角）/ 块级召回 R@k 的含义 / 你要读的那段代码里 `Counter` 与 `np.argsort` 在做什么。

## 🎯 切块不是超参，是把语义单元切碎的刀

RAG 的教程里，chunking 永远长成两个数字：`chunk_size=512, chunk_overlap=50`。它被归到"预处理"里，好像调不调无所谓。可一旦答案句被切开，后面所有环节都救不回来：embedding 只能读到块里的东西，重排器只能在候选里排，生成模型只能看到它被喂进来的那几百个 token。**检索链路是一条单向的漏斗，切块在漏斗最上面。**

这类失败有个共同长相：检索结果看起来完全正确。你问"a12 的阈值是多少"，top-1 返回的块里赫然写着 `the a12 threshold`，评审时没人觉得有问题；可后半句 `resolves to v31` 在相邻的那块里。模型拿着半句话被要求回答，答案只能靠编。用"命中率"衡量它，它是 1.000；用"答案召回"衡量它，它是 0.908。

所以我在这篇里把两个指标拆开测：

| 指标 | 定义 |
|---|---|
| **话题@5** | top-5 里至少有一个块包含查询的属性名（用户问的那个词出现了） |
| **答案@5** | top-5 里至少有一个块包含**完整**的事实句（属性和取值在同一块里，且连续） |

差出来的部分，就是"检索说它找到了"和"它真的找到了"之间的距离。

## 🔬 实验：120 篇手册、600 条事实、七种切法

语料是合成的模块手册，结构刻意贴近真实的工程文档：

- 120 篇，每篇讲一个模块，正文里夹着 5 条事实句，形如 `the a37 threshold resolves to v37 under sustained load`（9 个 token）；
- 其余是 ~190 token 的填充句，从 30 个常用词里随机抽，用来把事实句隔开；
- 额外放一份"交叉索引"文档：只把 600 个属性名密集列成表，一条取值都不带——真实世界里它叫目录页、API 索引、changelog；
- 600 条单跳查询（`what does a37 resolve to`）、30 条跨篇双跳查询（同时要两篇文档里的事实）。

检索用块级 TF-IDF + 余弦，idf 按块统计。**这是离线模拟，用 TF-IDF 代替 embedding、用合成语料代替真实文档**，测的是分块结构本身造成的损失，不代表任何具体模型的表现；真实 embedding 的分数分布更平滑，这里的结论方向成立、幅度会变。

七种切法：

```text
固定 64 / overlap 0        固定 64 / overlap 16      固定 64 / overlap 32
固定 128 / overlap 0       固定 128 / overlap 64
固定 256 / overlap 0       句界对齐 ~96（按句子打包到 96 token 上限）
```

## 🏗️ 五条机制

### 一、切断率由「单元长度 ÷ 块长」决定，与文档内容无关

固定切块的起点均匀撒在 token 流上。一个长 9 token 的事实句，只要起点落在它中间那 8 个位置之一，它就断成两半：粗估 `(L−1)/C = 8/64 = 12.5%`，实测 9.2%（600 条里 55 条被切断），块长翻到 128 时估 6.25%、实测 4.5%。估计偏保守偏高，因为块起点在每篇文档开头会重置，边界附近多了一层"不切断"的运气。

关键不在这个比例准不准，在于它**没有随机性可言**：切断的 55 条全部未命中，未命中的 55 条全部是切断的（100%）。这不是统计趋势，是确定性的结构性丢失——被切断的那一条，无论检索器多强都拿不回来。

顺带解释了为什么"话题@5"永远是 1.000：前半块里 `a37 threshold` 还在，它足够把这块顶进 top-5。检索器没做错任何事，它只是被喂了半句话。

### 二、加块长是最便宜的修法，账单在上下文里

固定 128 的索引 token 和固定 64 **完全相同**（23338）——块变大不改变总 token 数，只改变切点。切断率减半，答案@5 从 0.908 涨到 0.955，这是白拿的。

代价换了个地方记账：top-5 上下文从 311 token 涨到 410（+32%）。每次查询塞给模型的文本多了三成，这是真实的钱和真实的延迟（prefill 成本随上下文线性涨）。大块把"索引体积"换成了"每次查询的上下文体积"，而后者是持续开销、前者是一次性的。

继续加到 256：答案@5 与 top-1 都是 1.000，但 top-5 上下文 962 token，是固定 64 的 3.1 倍。同样的 4000 token 上下文预算里，256 的块塞得下 21 段，64 的块能塞 67 段——单跳看起来更准，多跳问题却先没预算了。

### 三、overlap 的收益在「≥ 最长语义单元」处封顶

overlap 的机制只有一个：保证任意长度不超过 `overlap+1` 的连续单元，必然在某一块里完整出现。事实句 9 token，overlap 16 就够——切断率从 9.2% 直接归零，答案@5 到 1.000。这是它唯一在做的事。

再往上加不会更安全，只会更多副本。o16→o32：切断率本来就 0，答案@5 本来就 1.000，什么都没涨；索引 token 从 29449 涨到 42804（+45%，相对 o0 是 +83%），块数从 522 涨到 769，top-1 反而从 0.955 掉到 0.905，重复槽从 0.17 涨到 0.32。

top-1 掉下去的原因是重复块在互相分票：同一段内容以三种偏移出现在三个块里，三块的向量几乎一样，分数被压成一小撮；而 idf 是按块统计的，事实句出现在越多的块里、它的 df 越高、判别力越弱。多出来的块没有提供任何新证据，只是把同一段话重新排进候选，还顺手稀释了真正有区分度的词。

同样的钱花在块长上回报更高：固定 128/o0 用 23338 token 拿到答案@5 0.955，固定 64/o32 用 42804 token 拿到 1.000 但 top-1 只有 0.905。前者索引小 45%，top-1 更高。

### 四、按文档去重会误删「完整的那一份」

双跳查询里，o16 的原始覆盖率 0.967，按文档去重后掉到 0.933；o32 更明显，0.967 → 0.900（换随机种子会浮动几个点，但从没见它涨过）。这不是噪声，是去重逻辑的必然：同一篇的第二块被删掉了，而**完整的事实句可能正好在第二块里**——第一块只有前半，第二块因为 overlap 才完整。去重按"来源"删，分不清"同一段的复印件"和"同一篇里的另一段证据"。

要去重就得按内容相似度去（块间 Jaccard 或向量距离阈值），或者干脆接受重复槽的存在，把 k 调大一点。按 doc_id 一刀切是最省事也最容易误伤的做法。

### 五、句界对齐是免费的

句界对齐没有调任何参数：按句子打包，超过 96 token 就断开，所以切点天然落在句号后。结果——切点全在句末，切断率 0，块均长 75，索引 token 23338（和固定 64 一模一样），答案@5 与 top-1 都是 1.000，top-5 上下文 459（固定 256 要 962）。

它同时赢了固定 64（答案 0.908）和固定 256（上下文 962），因为切点位置才是那个真正起作用的变量：块长决定"一段里能装多少"，切点决定"一段里装的是不是完整的"。真实文档里句子边界比合成语料更可靠——中文有句号、问号、分号，技术文档有标题层级和表格行；唯一要小心的是别在代码块、表格中间断。

## 💻 代码：切断率和两种指标的十行核心

```python
import numpy as np
from collections import Counter

def chunk_fixed(toks, size, overlap):
    """固定窗口：起点步进 size-overlap"""
    return [(i, min(i + size, len(toks))) for i in range(0, len(toks), max(1, size - overlap))]

def chunk_aligned(sents, target):
    """句界对齐：整句打包，超过 target 就断开"""
    out, cur, start, pos = [], [], 0, 0
    for s in sents:
        if cur and len(cur) + len(s) > target:
            out.append((start, pos)); cur, start = [], pos
        cur += s; pos += len(s)
    if cur:
        out.append((start, pos))
    return out

def contains(sub, seq):
    """完整事实句是否连续地出现在块里"""
    n = len(sub)
    return any(seq[i:i + n] == sub for i in range(len(seq) - n + 1))

# 两个指标分开算，一行都不能省
for f in facts:
    rank = search(["what", "does", f.attr, "resolve", "to"], chunks, idf, vecs, norms)
    topic_hit  = any(f.attr in chunks[i][1] for i in rank[:5])       # 提到这个词就算
    answer_hit = any(contains(f.tokens, chunks[i][1]) for i in rank[:5])  # 完整句才算
```

如果你只想在自己的语料上做一件事，就做这个：抽 200 条你关心的事实，写 15 行跑一遍，报出"话题命中 / 答案命中"两个数。绝大多数 RAG 的"检索没问题、回答不行"都能在这一步现形——两个数差多少，就是切块欠你多少。

## 💡 落地清单

1. **先量切断率，再调参数**。抽样事实句，检查完整性；切断率远高于 `(单元长度 ÷ 块长)` 说明切点撞在最差的位置上。
2. **overlap = 最长必须完整的单元**，不是某个百分比。事实句 9 token 就 16；如果一条答案靠的是整张表格，overlap 得覆盖表格高度，这时候该换策略而不是加数字。
3. **优先按结构切**：句号、段落、标题层级、表格行。结构对齐的收益（答案 0.908→1.000）比任何 overlap 调参都大，而且不涨索引。
4. **块长和 top-k 一起算账**。盯着"top-k 上下文 token 总量"这个数，它才是账单；固定 256 的 962 token 不是免费的。
5. **多跳问题单独测**。单跳 R@5 到 1.000 的策略，双跳@3 可能只有 0.900；双跳才是暴露重复槽和去重误伤的场合。
6. **别按 doc_id 去重**。要么按内容相似度，要么把 k 调大。
