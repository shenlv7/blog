> 压缩器没有删掉「采样率 16k」。
> 它删掉了「24k 会被重采样，VAD 直接失效」。
> 于是下游的 agent 知道该填 16k，却不知道这个数字为什么不能改。

**读这篇要会**：上下文窗口与 token 计费的基本概念 / agent 的会话历史与「摘要式记忆」是什么 / 会写 Python 的 HTTP 请求和循环。不需要 GPU，不需要 transformers，不需要读论文。

## 🎯 一件很日常的事，和一个被忽略的代价

任何跑得久一点的 agent 都会撞上同一面墙：会话历史越滚越长，每轮都要把前面所有内容重新塞进上下文。于是有了 compaction（压缩/摘要）：把前 N 轮交给模型，让它写一段几百字的摘要，替换掉原始历史，后面接着聊。

这套东西现在几乎到处都在用。Claude Code 会自动 compact，各家 agent 框架都带 `summary_memory`，论文里叫 hierarchical memory 或者 rolling summary。工程上它当然是划算的：一次压缩省下的 token 常常是几十倍。

问题是，压缩的定义是「保留后续任务需要的信息」。**谁来判断什么叫「需要」？**交给模型来判。而模型判断「需要」的标准，和你在下游真正需要的东西，未必是同一个集合。

我这篇想量一件事：当会话被压到不同预算时，**先死的是哪一类信息**。结论比我想的干净——

- 事实类信息（硬约束、已决事项、参数数值）非常抗压：压到 6 倍几乎无损，压到 18 倍还剩 75%。
- 理由类信息（这条约束为什么存在）**在任何一档压缩里都是全灭**。最宽松的那一档，事实 20/20 全活，理由 0/3。

顺序不是「重要的先留、次要的先丢」，而是**「能写成名词短语的先留、必须写成因果句的先丢」**。

## 🔬 实验怎么搭的

我没有真实产品的 trace（这很关键，下面「不能证明什么」里会讲），所以合成了一段 24 轮的会话：一个用户和一个助手在推进「博客 + 硬件项目」，会话里埋了 24 条事实和 3 条明确的「为什么」。

事实分四类：

| 类型 | 定义 | 例子 | 条数 |
|---|---|---|---|
| **C** 硬约束 | 不许违反的规则 | 报价一律人民币、不许出现美元 | 8 |
| **D** 已决事项 | 已经拍板的选择 | 向量库定 pgvector，放弃 Qdrant | 6 |
| **N** 参数数值 | 一个带原值的数字 | batch size 48、超时 6 秒 | 6 |
| **F** 噪声（控制组） | 应该被丢掉的寒暄 | 午饭吃了面、地铁晚点 | 4 |

再加 3 条 **W**：不是问「是什么」，而是问「为什么」——为什么品牌名必须统一、为什么放弃 Qdrant、为什么采样率必须是 16k。这三条的理由都写在会话原文里，句子完整、不含糊。

会话 3508 字。然后按三个预算各压一次：**400 字 / 150 字 / 60 字**，压缩指令是最朴素的那种（「压掉重复与寒暄，保留后续任务需要的信息」），温度 0。

然后对 27 条（24 事实 + 3 理由）逐条探测，共 4 个条件：全文、压到 400、压到 150、压到 60。每次探测都把对应版本的上下文整段塞进去，问一个问题，判分方式是**确定性关键词匹配**（答案里出现了判分词就算「记住了」）。一共 3 次压缩 + 108 次探测 = 111 次 API 调用。

先看压缩器自己的表现：

| 预算 | 实际摘要 | 超预算 | 摘要 token | 压缩倍数 |
|---|---|---|---|---|
| 400 字 | 603 字 | +51% | 357 | 5.8x |
| 150 字 | 334 字 | +123% | 200 | 10.5x |
| 60 字 | 191 字 | +218% | 117 | 18.4x |

第一件小事：**模型不守字数预算**。要求 400 字给了 603，要求 60 字给了 191——预算越紧，超得越多（+51% → +123% → +218%）。所以「压到 60 字」实际上只是「压到 191 字」。这个偏差本身值得记一笔：如果你的系统依赖「摘要必然不超过 X token」来做后续配额计算，这个假设是错的。

## 📉 结果：事实全活，理由全灭

| 类型 | 全文 | 压到 400 | 压到 150 | 压到 60 |
|---|---|---|---|---|
| C 硬约束 8 条 | 8/8 | 8/8 | 7/8 | 6/8 |
| D 已决事项 6 条 | 6/6 | 6/6 | 5/6 | 5/6 |
| N 参数数值 6 条 | 6/6 | 6/6 | 6/6 | 4/6 |
| **W 理由 3 条** | **3/3** | **0/3** | **0/3** | **0/3** |
| F 噪声 4 条 | 3/4\* | 0/4 | 0/4 | 0/4 |

\* 全文档那条 MISS 是判分噪声，不是记忆失败：原文写的是「去楼下吃面」，问题问的是「午饭吃的是什么」，模型答「未提及」。判分器对同义表述不鲁棒，这条我在正文里留着，不偷偷修掉。

看这张表要知道两件事。

**第一，事实真的很抗压。** 压到 603 字（5.8 倍）时，20 条事实**一条没丢**：人民币、禁外链、pgvector、新加坡区、node20、48、3e-5、6 秒、8G、16k、12 万……连「报价整百取整」这种一句话里塞两条的细节都在。摘要写得像一份工整的规格清单。

**第二，理由是断崖，不是斜坡。** 3/3 → 0/3，中间没有过渡。我把三份摘要全文拉出来做了个机械统计：

> 原文出现因果连词（因为 / 原因 / 由于 / 为了 / 避免 / 否则 / 以免 / 所以）共 **4 处**；
> 三份摘要里的因果连词数：**0、0、0**。
> 三份摘要里的数字个数：**23、18、12**。

数字几乎原封不动地被搬了过去，因果一个没留。604 字的那份摘要，读起来完美无缺——如果它是一份交接文档，接手的人会把每一条都执行得很好；**但如果他要把「16k」改成「24k」，他没机会知道这会在 VAD 上踩坑。**

继续往下压，事实开始掉，而且掉得有规律：

- **150 字档掉了 2 条**：c8「哪两条要写进 AGENTS.md 置顶」（要求一句话里同时点名品牌名和人民币）和 d4「索引页不写 seriesOrder」。
- **60 字档再掉 3 条**：c4「UI 禁 emoji、但正文 emoji 保留」（一个事实，两个分叉）、n3「GitHub 超时 6 秒」、n6「预算 12 万」。

掉的 5 条里，4 条是**关系型事实**——需要两个元素同时在场才成立的判断：「UI 和正文不同待遇」「品牌名和人民币要成对置顶」。压缩器写摘要时倾向于把每个主语各写一条短句，「A 禁 X、B 保留 X」在它看来是可以合并同类项的重复，一合并，区分就没了。而「超时 6 秒」这种，容易和「重试」合并成一句「6 秒 + 重试」再在压缩中整个消失——因为它看起来像一个「已经说过的工程细节」。

对比一下噪声组：4 条噪声在**每一档压缩里都被干净利落地全丢**（0/4）。这一点都不意外，也说明压缩器的工作正常——它确实在做取舍，只是取舍标准是「像不像寒暄」，不是「下游用得上用不上」。

## 🏗️ 为什么会这样：压缩器优化的不是「可复算性」

用一句话概括这个机制：**摘要的优化目标是「压缩后读得懂」，不是「压缩后还能重新决策」。**

形式化一点。设压缩算子为 `C`，原文为 `x`，事实集合 `F`，理由集合 `W`，`a(f, ctx)` 是「拿上下文去回答关于 f 的问题」这个动作。我们真正在意的是两个不一样的量：

```text
P_fact(C) = (1/|F|) · Σ_{f∈F} 1[ a(f, C(x)) == f ]     # 事实存活率
P_why(C)  = (1/|W|) · Σ_{w∈W} 1[ a(w, C(x)) == w ]     # 理由存活率
ρ         = L(x) / L(C(x))                              # 压缩率（长度比）
```

实验做的就是把 `ρ` 从 1 推到 5.8、10.5、18.4，然后看这两条曲线怎么分开。

它们分开的原因是结构性的，我数出三条：

**一、理由在信息论上「冗余」，在决策上「唯一」。** 「16k 采样」这五个字自带一个数字，压缩器知道它是规格；「因为 24k 会重采样导致 VAD 检测不到句尾」是 18 个字的因果链，里面没有新参数、没有新决定，全都服务于一个已经做出的决定。**一个已经做完的决定，它的推导过程在摘要视角里就是过程垃圾。** 这就是为什么理由不是被「压缩」掉的，是被「判定为已完成」而丢弃的。

**二、摘要器逐条重写，天生不擅长成对关系。** 摘要是并列短句的集合，「A 禁 X」和「B 保留 X」在生成时是两个独立句子，除非模型主动意识到它们的对照关系，否则必然被写成一句「UI 禁 emoji」——信息量看起来没少，只有对照没了。所有「成对才成立」的约束都吃这个亏。

**三、损失是不可见的。** 这是最麻烦的一条。事实被丢掉，下游 agent 会答「未提及」，你能发现；理由被丢掉，下游 agent 会答得**又快又自信**——它知道 16k，知道这是规格，问它能不能改成 24k 它会说「可以，先试试」。压缩出的错误没有报错，只有静默。

所以我更愿意把这件事叫**可审计性衰减**（auditability decay），而不是信息衰减。会话记忆里原本存着「决定 + 依据」，压缩后只剩「决定」。依据一没了，后续所有「这个决定还能不能改」的判断都失去输入——长会话 agent 越跑越离谱，一部分根源在这里：它不是忘了规则，它是忘了规则的边界，于是把规则当成了可以优化的默认值。

## 💻 核心代码

完整脚本（含 24 轮会话原文、27 条探测、判分器）在仓库：[demos/ai-concepts-62-context-compaction.py](https://github.com/shenlv7/blog/blob/main/demos/ai-concepts-62-context-compaction.py)。这里贴三段骨。

```python
def compact_prompt(budget):
    return (f'把下面这段对话压缩成不超过 {budget} 字的中文摘要，压缩掉重复与寒暄，'
            '保留后续任务需要的信息。只输出摘要，不要解释。')

def hit(req, answer):
    """确定性判分：答案里出现任一关键词就算『记住了』"""
    a = answer.replace(' ', '')
    return any(r.replace(' ', '') in a for r in req)

def probe(fact, context, label):
    msg = ('下面是一段项目会话记录。只依据记录回答，记录里没写的就回答「未提及」。'
           f'答案控制在 30 字以内，不要解释。\n\n=== 记录开始 ===\n{context}\n'
           f'=== 记录结束 ===\n\n问题：{fact["q"]}')
    ans, _ = chat([{'role': 'user', 'content': msg}], max_tokens=60)
    return dict(fact=fact['id'], kind=fact['kind'], cond=label,
                ok=hit(fact['req'], ans), ans=ans[:80])
```

关键设计就一条：**判分和生成分开**。生成用 LLM，判分用字符串匹配，这样「模型没记住」和「裁判觉得没记住」不会混在一起。代价是判分会高估（下面会讲）。

如果你想给自己系统的压缩做个同类体检，把这段拿去过一遍就行：

```python
PINNED = [  # (事实, 问题, 判分词) —— 从你的系统提示词、硬约束里抄 8-10 条
    ('报价一律人民币', '对外报价用什么货币？', ['人民币']),
    ('UI 禁 emoji，正文保留', 'UI 能用 emoji 吗？正文呢？', ['禁', '不许']),
]
def audit(compact_fn, probe_fn):
    bad = [(f, probe_fn(f, q)) for f, q, req in PINNED
           if not any(r in probe_fn(f, q) for r in req)]
    return bad   # 存活率 < 90% 就别用这版摘要，改用『置顶块 + 最近 N 轮截断』
```

## 🩹 我第一版为什么是废的

第一版我埋了 12 条事实、会话只有 9 轮、预算给 400 字。跑出来的结果是：全文 12/12，压缩后 10/12，丢的两条**正好都是噪声**。

我差点就写成「压缩是无损的，放心用」——一个看起来很漂亮、方向完全反了的结论。

废在哪？**压缩比只有 6 倍，摘要预算比信息量还大，压缩器根本不需要取舍。**你让一个人把 2000 字的会议记录缩到 600 字，他会把寒暄删掉然后停手；你让他缩到 100 字，他才开始挑「哪些决定必须留」。我要测的是取舍行为，却给了它一个不必取舍的预算——测出来的是它的下限，不是它的策略。

第二版加了预算扫描（400/150/60）和「为什么」探测，机制才露出来。

还有一个更蠢的坑，顺手记在这：第二版第一次跑完，c4（「UI 禁 emoji、正文保留」）在**四个条件里全 MISS**，包括全文档。我第一反应是「模型连原文都答不对，判分有问题吧」，然后去翻原始回答——回答是「UI 禁 emoji；正文保留」，答得完全正确，是我判分词列表里漏了「禁」这个字。

**教训：一条题在全条件里都 MISS，先怀疑判分器，别怀疑被测对象。**这也是上面那个「生成和判分分开」设计的另一面：分开之后，判分器自己的 bug 会被单独暴露，只是你得记得去看原始输出。

## 🧭 落到工程上怎么做

**一、别把硬约束放进会被压缩的东西里。** 给 agent 一个不参与压缩的置顶块（system prompt 或 `AGENTS.md`），里面只放两样：不能违反的规则 + 每条规则**为什么**存在。会话历史只压「过程」。这条的成本几乎为零，收益最大——你的约束在每一轮都重新出现在最显眼的位置，也就不会出现「压缩器觉得这条已经说过了」。

**二、摘要里必须带依据，而且要当成格式要求。** 别写「保留重要信息」，写具体格式：`每条决定后面必须附一行「依据：…」`。我这轮**没有**对这个做对照（第一版试过「硬约束必须逐条保留」，结果和朴素指令一样是 19/24——因为那一版事实本来就全活着，指令没有可发挥的空间，等于没测到），所以这条只是从机制推出来的建议，不是实测结论。要验证，拿上面对账脚本跑一次就行。

**三、压完必须自检，不能默认「摘要成功 = 记忆正确」。** 10 条探针打一遍，存活率低于 90% 就拒绝这版摘要，退化成「置顶块 + 最近 N 轮原文截断」——宁可多花 token，也别让 agent 带着一份缺依据的记忆往下跑。

**四、给「为什么」单独一条通道。** 我的做法是决策日志（`docs/decisions.md`）：每次拍板写一行「决定 / 依据 / 反例」。这个文件从不进压缩流程，agent 每次需要判断「这条能不能改」时去查。压缩负责省 token，决策日志负责守住可审计性，两件事分开做，比指望压缩器同时干好更靠谱。

## ⚠️ 这篇不能证明什么

按老规矩，边界写清楚：

- **不是真实产品 trace。** 会话是我合成的，而且理由写得比真实对话完整——真人不会每次都把「为什么要这样」说得这么清楚。真实的会话只会更难，所以这条偏差的方向是「我高估了压缩器的表现」。
- **判分是关键词匹配，会高估记忆。** 只要答案里出现判分词就算过。压到 60 字那档，c3 的回答里混进了「正文禁外链」这种不相干内容，仍然被算对——它在「蒙对」。
- **n=27，单个模型、单次运行、中文、温度 0。** 没有置信区间可言，我不打算把 0/3 说成「理论上必然为 0」，只说「这一组设置下三次都是 0」。换模型、换语言、换压缩器，数字会变。
- **噪声组全灭是设计预期，不是缺陷。** 它证明的是压缩器在正常工作，别把它算进「损失」。
- **没测累积压缩**（压完再压），也没测「压缩后继续对话、再从新摘要里取信息」的二次衰减。从我第一版的经验看，累积压缩才是真正会崩的地方，那需要另一次实验。
- **不涉及 GPU、显存、吞吐**，纯 API 行为测量。111 次调用，没什么成本，但也不是生产规模的压测。

一句话收尾：**压缩器是很听话的实习生，你让它省字它就省字，它会把所有「是什么」抄整齐，然后把所有「为什么」当成解释性废话删掉——因为它没法知道，你后面要靠这些废话来决定什么能改。**
