> 20000 条样本、中位长度 277 token 的长尾分布，按长度随机凑批：
> **bs=8 时 37.5% 的前向 token 是真 token，bs=64 时只剩 19.0%**。
> 也就是说 batch 越大，算力里补零的比例越高——从 62% 涨到 81%，五次前向里有四次在算 PAD。
>
> 这不是浪费在数据上，是浪费在**同一组里最长的那条样本**上：组内最大值定死了整组的形状。
> 长度分桶把利用率拉回 98.5%，FFD 打包进 4096 的定长窗口能到 99.9%。
>
> 但打包不是免费的：8 篇文档拼成一条 2048 token 的序列后，每个 token 可见的键里有 **77.8%** 属于别的文档。
> 不补边界掩码，这些键分走 **81.5%** 的注意力质量；补上就是严格的 0，代价是每层 4 MiB 的 2048² 布尔矩阵。

读这篇要会：Transformer 的因果注意力是怎么算的 / 训练时 batch 与 padding 的关系 / 对数正态分布。

## 🎯 一条样本多长，不是你能定的

训练语料里「一条样本」的长度是分布，不是常数。客服对话、代码文件、论文摘要混在一起，长度差两个数量级是常态。而 GPU 要的是矩形张量：`[batch, seq_len]`。中间那一步转换就是 padding——把短的补到组内最长。

补出来的 PAD 不做任何事，但它参与矩阵乘、占显存、走完整个前向反向。这部分算力是纯开销，而且**开销比例由组内最长的那条样本决定**，跟组里其他样本多短无关。

利用率可以写成一个式子。对一个 batch 组 $b$，组内长度为 $L_i$：

$$
U=\frac{\sum_{b}\sum_{i\in b} L_i}{\sum_{b}\left(\max_{i\in b}L_i \cdot |b|\right)},\qquad
\text{浪费}=\frac{\sum_b (\max_{i\in b}L_i)\cdot|b| - \sum_b\sum_{i\in b}L_i}{\sum_b (\max_{i\in b}L_i)\cdot|b|}
$$

分子是真实 token，分母是实际做矩阵乘的 token。$|b|$ 是组大小。式子只有三个变量：长度分布、组大小、以及**组内怎么配对**。前两个你改不了，第三个是全部工程空间。

我用一份贴近真实语料的长度分布跑了账：对数正态，中位 277 token，σ=0.85，裁到 [40, 4096]。20000 条样本合计 7,931,451 个真 token，P90 是 820，P99 是 1979。

## 🔬 实验 A：补零的账，随 batch 变大而变糟

`pad_cost` 就是上面那个分母的直接实现——按给定顺序每 `bs` 条一组，各自补齐到组内最长，然后求和。

```python
def pad_cost(order, bs):
    """按给定顺序、每 bs 条一组，各自补齐到组内最长。"""
    total = 0
    for s in range(0, len(order), bs):
        chunk = L[order[s:s + bs]]
        total += chunk.max() * len(chunk)
    return total
```

真实 token 固定 7,931,451。跑出来的账：

| 策略 | 前向 token | 利用率 | 是真实量的 |
|---|---:|---:|---:|
| 朴素 batching, bs=1 | 7,931,451 | 100.0% | 1.00× |
| 朴素 batching, bs=2 | 11,476,384 | 69.1% | 1.45× |
| 朴素 batching, bs=4 | 15,922,316 | 49.8% | 2.01× |
| 朴素 batching, bs=8 | 21,154,840 | 37.5% | 2.67× |
| 朴素 batching, bs=16 | 27,060,784 | 29.3% | 3.41× |
| 朴素 batching, bs=32 | 33,876,160 | 23.4% | 4.27× |
| 朴素 batching, bs=64 | 41,816,960 | 19.0% | 5.27× |
| 长度排序 batching, bs=8 | 7,945,832 | 99.8% | 1.00× |
| 长度排序 batching, bs=32 | 7,994,176 | 99.2% | 1.01× |
| 长度排序 batching, bs=64 | 8,055,232 | 98.5% | 1.02× |
| 桶内乱序 + 组内排序, bs=8 | 8,286,408 | 95.7% | 1.04× |
| 贪心打包, bin=4096 | 8,835,072 | 89.8% | 1.11× |
| FFD 打包, bin=4096 | 7,938,048 | 99.9% | 1.00× |

第一列往下看，利用率从 100% 掉到 19%。这不是因为样本变短了，而是因为**组内最大值的期望随组大小单调上升**：抽 $B$ 个对数正态样本，最大值的量级大约是 $e^{\mu+\sigma\sqrt{2\ln B}}$。bs 从 8 到 64，$\sqrt{2\ln B}$ 从 2.04 涨到 2.88，长度期望乘上 $e^{0.85\times0.84}\approx2.0$——长尾那一侧被反复摸到，整组跟着变长。

所以「加大 batch 提高 GPU 利用率」这句话只在**算力层面**成立。在**有效算力层面**，朴素实现里边加 batch 边给自己加税：bs=8 每组 2.67 倍开销，bs=64 就是 5.27 倍。你把 batch 从 8 提到 64 想换来更好的并行度，顺手把 3.4 倍的前向算力送给了补零。

## 🏗️ 三种省法，差别在「谁决定形状」

**长度分桶**（length bucketing）不改数据，只改顺序：把长度接近的样本放进同一组，组内最大 ≈ 组内平均。bs=64 时利用率 98.5%，开销几乎归零。真实实现不会全量排序——那会让每个 step 只看到同一类长度、破坏随机性——而是**桶内乱序、组内排序**：把长度排序后的样本切成 200 条一桶，桶内打乱，再在 micro-batch 内按长度排。这个版本 bs=8 时是 95.7%，损失 4 个点换回随机性。

**打包**（packing）换的是另一件事：不再补零，而是把多条样本首尾相接塞进一个定长窗口，用一条长序列喂进去。定长窗口的意义是形状固定——kernel 只编译一次，没有动态 shape 的重编译和碎片。代价是实现要处理「这一条序列里其实有好几篇文档」。

打包本身是个装箱问题：窗口 4096，样本 40~4096 长，怎么塞。按长度降序贪心装（装不下就开新箱）是 89.8%——比长度分桶还差，因为每个箱子剩下的零头全按 4096 计费。换成 FFD（first-fit decreasing，长样本先放，塞进第一个装得下的箱子）就能到 99.9%：剩下的空隙不超过最短样本，20000 条摊进 1938 个箱子里，浪费 6,597 个 token。

**变长核**是最彻底的一种：连矩形都不要了，直接把 `cu_seqlens`（累积长度表）交给 FlashAttention 的 varlen 接口，每个 batch 只算真实 token。利用率 100%，因为根本没有 PAD。代价是 kernel 侧的约束——变长核的并行划分按真实 token 数走，batch 内长度差太大时负载不均；而且你放弃了定长窗口带来的形状稳定性。

三种做法的取舍可以一句话概括：**分桶省得最多、改动最小；打包形状最好、语义最脏；变长核最干净、最挑框架**。

## 💻 实验 B：拼起来以后，边界去哪了

把 8 篇文档拼成一条 2048 token 的序列（长度 64/96/128/160/224/288/416/672），因果注意力下每个 token 都能看见自己之前的所有 token——包括前面 7 篇的。这是打包语义上的直接后果，不是 bug。

先做纯计数，这一部分是确定的：token 在文档内的偏移是 $i$，文档起点是 $s$，它能看见 $s+i+1$ 个键，其中 $s$ 个属于别的文档：

$$
\text{外来可见比例}=\frac{s}{s+i+1}
$$

| 文档 | 长度 | 起点 | 可见键外来占比 | 首 token 可见外来 | 实测外来注意力 |
|---|---:|---:|---:|---:|---:|
| 0 | 64 | 0 | 0.0% | 0.0% | 0.0% |
| 1 | 96 | 64 | 60.8% | 98.5% | 88.6% |
| 2 | 128 | 160 | 73.3% | 99.4% | 63.2% |
| 3 | 160 | 288 | 79.4% | 99.7% | 55.9% |
| 4 | 224 | 448 | 81.0% | 99.8% | 93.4% |
| 5 | 288 | 672 | 83.2% | 99.9% | 98.1% |
| 6 | 416 | 960 | 83.0% | 99.9% | 81.0% |
| 7 | 672 | 1376 | 81.4% | 99.9% | 87.2% |

整体：可见键里 77.8% 属于别的文档。**最后一篇文档的第一个 token，99.9% 的可见上下文是别人的内容**——它在这一步里学到的表示，几乎完全由前面 7 篇无关文档决定。

「实测外来注意力」这一列是不加边界掩码、用随机投影的 Q/K（64→32 维）在 numpy 上算出的真实注意力权重（不是训练过的模型，所以分布是弥散的；它衡量的是几何事实：可见键里外来键占多少，注意力就会按比例分出去多少）。实测 81.5%，比 77.8% 的键占比略高，但这个差值不稳定——换个 Q/K 的种子就会动。**与分布无关的是 77.8% 这个计数**：无论模型学到什么，那些键都在视野里。

加上文档边界掩码后，这一项是 0，严格为 0，不是接近 0：

```python
s = Q @ K.T / np.sqrt(D_HEAD)
allowed = causal & (doc_of[:, None] == doc_of[None, :])   # 因果 + 同文档
s = np.where(allowed, s, -np.inf)
P = softmax_rows(s)
```

这四行是打包正确性的全部——漏掉第二项，训练照样收敛，loss 曲线照样漂亮，只是每条样本都在偷看邻居。这类错误不会报错，只会让指标对不上。

掩码本身要付内存：2048×2048 的 bool 矩阵建出来是 4.0 MiB 一层，32 层堆叠期间就算复用也要按峰值算；打包成 bit 是 0.5 MiB；而 `cu_seqlens` 只是一张 8 个 int32 的表。这是为什么生产实现走 varlen 接口而不是显式掩码——**边界信息应该存在长度表里，不应该存在权重里**。

## 💡 落地清单

- **先量长度分布再选策略**：P50 和 P99 差 7 倍以上（也就是这份数据的 277 和 1979），分桶和打包都有意义；如果长度几乎恒定，改这些是白干。
- **分桶是第一选择**：改动只在 DataLoader，利用率从 37.5% 到 99.8%，且不碰模型语义。
- **打包必须配边界掩码**，掩码要和 `doc_of` 一起从 collate 函数传进模型，别在 attention 里临时用位置算——算错的概率远高于你想象。
- **定长窗口的零头要认账**：FFD 的 99.9% 来自「先放长的」；顺序贪心只有 89.8%，差的那 10% 就是每个箱子的尾巴。
- **batch 大小和序列长度的预算一起吃**：bs=64 的 5.27 倍开销，等价于你实际只有 19% 的算力在干活；先修这个，再谈加卡。
