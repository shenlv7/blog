# AI核心概念(23)：投机解码 Speculative Decoding——小模型抢答、大模型判卷

> "自回归解码每一秒只做一件事：把整套权重从显存里读一遍，就为了吐出一个 token。既然读一遍权重的价钱是固定的，那就别只让它判一道题——让它一次判一整张卷子。"

## 🎯 前提：解码阶段贵的不是计算，是"阅读量"

先接上期的账。上一期（KV 缓存）算过：预填充 prefill 阶段能把 GPU 算力跑满，而逐 token 的**解码 decode 阶段**算力根本吃不满——每个 token 都要把权重矩阵从显存搬到计算单元，时间是"权重字节数 ÷ 显存带宽"，跟你要算多少没关系。所以：

- 一个 7B 模型用 FP16 存权重是 14 GB，一张 2 TB/s 带宽的卡上，光是"读一遍权重"就要 7 ms，而算力上它只需要几十微秒。
- 每个 token 都重复这 7 ms。生成 1000 个 token 就是 7 秒，其中真正的算术只占个零头。

**投机解码**（speculative decoding）就是冲着这个浪费去的：

```python
# 一轮投机解码（γ = 草稿长度）
drafts = draft.propose(ctx, gamma)          # 小模型（或查表）先猜 γ 个 token，串行但便宜
logits = target(ctx + drafts)               # 大模型一次前向，同时判这 γ+1 个位置
accept = 最长前匹配前缀                     # 挨个比：我要的下一个 token 是不是你猜的那个
out += accept + [target_resample(断点)]     # 至少赚 1 个 token，运气好赚 γ+1 个
```

术语当场对齐一遍（后面公式里会反复用）：

| 记号 | 含义 |
|---|---|
| 目标模型 target | 你真正想要的那个大模型，输出质量的唯一标准 |
| 草稿模型 draft | 负责抢答的小模型 / 查表，可以不准，但必须**便宜** |
| γ | 草稿长度：一轮猜几个 token |
| α | 接受率：草稿的提议被目标模型认可的比例 |
| τ | 平均接受长度：一轮平均净赚多少 token（EAGLE 论文里就用它当指标） |
| c | 成本比：草稿一步 / 目标一步的耗时比 |

一句话概括这套买卖：**算法上多做了一大堆计算（草稿的前向是纯浪费的），换的是目标模型"串行步数"变少。** 所以它的收益从来不是免费的，而是"用多余的算力买延迟"——这句话既是它有效的原因，也是它失效的原因，后面两个反例会各证一次。

## 🔬 账本：一轮到底能赚多少

只需两个量就能把账算清（推导极其简单：设每次接受概率独立为 α，则一轮接受 k 个的概率是 α^k(1-α)，求和即可）：

```text
E[接受数] = (1 - α^(γ+1)) / (1 - α)          # 含那个"奖励 token"
加速比    = E[接受数] / (1 + γ·c)             # 分母：1 次目标前向 + γ 次草稿前向
```

把公式铺开看两张表（α 是横轴，γ 是纵轴）：

```text
　γ\α      0.5     0.6     0.7     0.8     0.9      E[接受]@α=0.8
   1     1.36    1.45    1.55    1.64    1.73              1.80
   2     1.46    1.63    1.82    2.03    2.26              2.44
   4     1.38    1.65    1.98    2.40    2.93              3.36
   6     1.24    1.52    1.91    2.47    3.26              3.95
   8     1.11    1.37    1.78    2.40    3.40              4.33
  12     0.91    1.13    1.50    2.15    3.39              4.73      ← c = 0.10

　γ\α      0.5     0.6     0.7     0.8     0.9
   4     0.97    1.15    1.39    1.68    2.05                       ← c = 0.25
   8     0.67    0.82    1.07    1.44    2.04
  12     0.50    0.62    0.83    1.18    1.86
```

最优草稿长度（把 γ 扫到 32 找最大值）：

| α | c=0.10 → 最优 γ / 最佳加速 | c=0.25 → 最优 γ / 最佳加速 |
|---|---|---|
| 0.5 | 2 / **1.46x** | 1 / **1.20x** |
| 0.6 | 3 / 1.67x | 2 / 1.31x |
| 0.7 | 4 / 1.98x | 2 / 1.46x |
| 0.8 | 6 / 2.47x | 3 / 1.69x |
| 0.9 | 10 / 3.43x | 6 / 2.09x |

四处读数，全部来自上面两行公式：

1. **α 决定上限，γ 只能在 α 允许的空间里优化。** α=0.5 时无论草稿写多长，加速比都压在 1.5x 以下；α=0.9、c=0.10 才摸到 3.4x。这就解释了为什么这个领域十年来的主要工作都在"提高 α"（训练草稿头、草稿树、检索草稿），而不是"加长草稿"。
2. **γ 边际递减。** α=0.8 时 E[接受] 从 γ=4 的 3.36 涨到 γ=12 的 4.73——草稿长度翻三倍，只多赚 1.4 个 token；分母里的 γ·c 却是线性的。所以最优 γ 卡在 4-6 附近。
3. **c 是真正的杠杆。** 同一个 α=0.8，c 从 0.10 变成 0.25，最优 γ 就从 6 掉到 3，最佳加速比从 2.47x 掉到 1.69x。
4. **c=1 时加速比恒等于 1.00x。** 草稿和目标一样贵的话，α 再高也白搭：分母变成 1+γ，分子是 γ+1，正好抵消。投机解码买的是"草稿便宜"，不是"草稿聪明"。

公开锚点可以对一下（这些是论文报告的实测，不是我的数）：

- Leviathan 等（**arXiv:2211.17192**，ICML 2023）：T5-XXL 上相比标准 T5X 实现 **2x-3x**，输出完全不变。
- Chen 等（**arXiv:2302.01318**，Chinchilla 70B）：**2-2.5x**，并强调"在硬件数值精度内保持目标模型的分布"。
- EAGLE-2（**arXiv:2406.16858**）：以 Vicuna-68M 做草稿的标准投机采样在 Vicuna-7B 上是 **1.50x**，EAGLE-2 自己报告 **3.05x-4.26x**，平均接受长度 τ 4.0-5.5。

看第一行和第三行的差距：**同样叫"投机解码"，1.50x 和 4.26x 的分水岭就在草稿头上**。下面本机实测部分会把这个分水岭亲手复现一遍。

## 🧪 实测一：草稿不是"随便找个小模型"

我在本机搭了个纯 numpy 的玩具 GPT 来验证机制：目标模型 8 层、d=128、4 头，词表 64（随机初始化，不训练——测的是机制，不是某个真实模型的加速比）。草稿一律只用**前 2 层**（成本约 1/4），唯一的变化是输出头：

| 草稿 | argmax 一致率 |
|---|---|
| 未对齐（直接用共享输出头） | **0.046** |
| 线性蒸馏对齐（岭回归拟合） | **0.550** |
| 完美草稿（就是目标模型本身） | **1.000** |

"未对齐"就是字面意思：2 层随机网络的 argmax 和 8 层目标几乎没有关系（0.046 基本是巧合）。**这说明"拿个小模型当草稿"这个直觉是错的**——小模型必须被专门对齐到目标模型的输出分布上，这正是 EAGLE / Medusa / MTP 都要训练草稿头的原因。

我这个玩具用的是最省事的对齐方式：拿目标模型的隐状态和 logits 做一次**岭回归**（本质是最简形式的蒸馏）——目标模型在 60 个随机上下文 + 自己生成的 3×256 步上提供监督，闭式解拟合一个 128×64 的线性头，相对误差 0.326，argmax 一致率从 0.046 升到 **0.550**。注意数据里有"目标模型自己生成的序列"这一半：蒸馏数据本来就该取自目标模型的分布，而不是均匀随机分布。

```python
class Draft:
    """草稿 = 目标模型的前 2 层 + 一个线性对齐头（蒸馏的最简形式）"""
    def __init__(self, base, W=None):
        self.base, self.W = base, W
    def forward(self, ids, cache=None):
        h, cache = self.base.body(ids, cache)
        return (h @ self.base.emb.T if self.W is None else h @ self.W), cache


def fit_align(target, base, n_rand=60, n_gen=3, gen_len=256, ridge=1e-3):
    X, Y = [], []
    for _ in range(n_rand):                      # 一半：随机上下文
        ids = np.array(RNG.integers(0, V, 16))
        X.append(base.body(ids, None)[0]);  Y.append(target.body(ids, None)[0] @ target.emb.T)
    for _ in range(n_gen):                       # 一半：目标模型自己生成的轨迹
        logits, tc = target.forward(np.array(ctx0), None)
        _, dc = base.body(np.array(ctx0), None)
        for _ in range(gen_len):
            tok = int(np.argmax(logits[-1]))
            h2, dc = base.body(np.array([tok]), dc)
            h8, tc = target.body(np.array([tok]), tc)
            X.append(h2);  Y.append(h8 @ target.emb.T);  logits = h8 @ target.emb.T
    X, Y = np.concatenate(X), np.concatenate(Y)
    A = X.T @ X + ridge * len(X) * np.eye(X.shape[1])
    return Draft(base, np.linalg.solve(A, X.T @ Y))
```

## 🧪 实测二：真实接受率、逐位无损、以及一条容易搞混的口径

跑 32 个 token（提示词 16 个），γ 取 2/4/8，温度取 0.3/1.0/2.0，共 9 组：

```text
T=1.0  γ=2  α=Σmin(p,q)=0.880  命中 14/36=0.389  每轮产出 1.78  目标前向 19（基线 33） 草稿前向  54  墙钟 0.72x  逐位一致=True
T=1.0  γ=4  α=Σmin(p,q)=0.878  命中 14/72=0.194  每轮产出 1.78  目标前向 19（基线 33） 草稿前向  90  墙钟 0.55x  逐位一致=True
T=1.0  γ=8  α=Σmin(p,q)=0.877  命中 16/128=0.125 每轮产出 2.00  目标前向 17（基线 33） 草稿前向 144  墙钟 0.47x  逐位一致=True
（温度 0.3 / 2.0 的三组同样逐位一致，命中和产出完全一样，只有计时抖动）
```

先看最重要的一列：**9 组全部与朴素贪心解码逐位一致**。这不是"差不多"，是 token id 序列逐个相等——投机解码在贪心模式下是无损的，因为它接受的是"目标模型自己的 argmax"，拒绝时又用目标分布的 argmax 顶上。

然后是那条容易搞混的**口径**，我在这里踩过一次：

- `α=Σmin(p,q)` 是**采样模式**下的接受概率（对分布逐项取 min 再求和），我实测是 0.87-0.94；
- 但贪心模式（temperature=0）下决定"接不接受"的，是两个分布的 **argmax 是否相等**，实测命中率只有 0.389-0.125。

温度只改变分布的形状，不改变 argmax——所以那张 α 表在贪心模式下**没有意义**，真账是命中率那列。看到网上有人拿 Σmin 的 α 去解释自己的贪心加速比，那个数是虚高的。

再看按草稿位置拆开的命中率（EAGLE 口径，每一轮的所有位置都独立统计，拒绝点之后用反事实前缀评估）：

```text
草稿位置     0      1      2      3      4      5      6      7
尝试次数    16     16     16     16     16     16     16     16
命中率    0.375  0.625  0.438  0.500  0.688  0.438  0.500  0.438
```

在这台玩具上它基本是平的——因为这个草稿头没有"越往后误差越累积"的结构。真实系统里 EAGLE 报告的是明显的位置衰减（越靠后越容易猜错），所以它们才要在草稿树里做剪枝：**把草稿预算花在还没跑偏的分支上，而不是均匀铺满 γ 个位置。**

## 🧪 实测三：两个反例，和"为什么本机 CPU 上反而变慢"

```text
朴素自回归（33 次目标前向）                 :  250.6 ms   1.00x
γ=2  对齐草稿（目标前向 19 草稿前向  54）   :  359.0 ms   0.70x
γ=4  对齐草稿（目标前向 19 草稿前向  90）   :  473.1 ms   0.53x
γ=8  对齐草稿（目标前向 17 草稿前向 144）   :  562.2 ms   0.45x
反例1 未对齐草稿（γ=4）                     :  840.3 ms   0.30x
反例2 完美草稿（=目标本身，成本一样，γ=4）  :  364.7 ms   0.69x
成本比实测 c = 草稿一步 1.77 ms / 目标一步 6.94 ms = 0.255
```

三个读数：

1. **目标前向次数确实降了**：33 次降到 17-19 次（约 1.8x 少）。算法层面它完全按预期工作——每一次前向都在批量判好几个 token。
2. **但墙钟是 0.45x-0.70x，越长的 γ 越慢。** 原因在下面那张表：本机（CPU + numpy）上"验证 k 个 token"并不免费。

```text
    k   批量一次(ms)   k 次单喂(ms)   批量/单喂
    1          6.93           6.85       1.01
    2         11.23          13.84       0.81
    3         13.84          20.77       0.67
    5         15.96          35.01       0.46
    9         15.78          63.22       0.25
```

批量喂 9 个 token 只花 0.25×9 的单步时间——因为 CPU 上单步的耗时大半是 numpy 的固定调用开销，多喂 token 的边际成本很低。**方向对了，但不够便宜**：这里每一轮要花"1.75 步"去验证（k=5），再花 4×0.255=1.02 步去起草稿，总共 2.8 步换 1.8 个 token——还是不划算。GPU 上同一件事的成因完全不同（解码阶段显存带宽受限，权重读一遍就是全部成本，喂 1 个还是 k 个 token 的耗时几乎一样），那个前提下同样的 α 和 γ 才能变成 2x-3x。

一句话：**投机解码是"拿算力买延迟"的交易，能不能成交取决于硬件瓶颈在带宽还是算力。** 我的玩具在算力/调用开销这一侧，所以成交价是亏的——但这恰好证明了公式里的分母不是装饰。

3. **两个反例各自钉死一个前提。** 反例 1（未对齐草稿）0.30x：注意它的 `Σmin(p,q)=0.647` 看着不差，但**贪心命中率是 0.000**——72 个草稿 token 一个都没被接受，全是白跑的前向，所以最慢。反例 2（完美草稿）0.69x：α=1.000，一个 token 都不用重采，但**一点都不省**，因为 c≈1——所以"草稿越准越好"也不对，要的是"又便宜又准"。

## 🏗️ 换一个几乎免费的草稿：查表（Prompt Lookup Decoding）

既然胜负手是 c，那就把 c 干到 0。**PLD**（Saxena 2023）连草稿模型都不要：

```python
def ngram_propose(ctx, gamma, n=3):
    """把上下文最后 n 个 token 当模板，去前面找同款，抄它后面的 token 当草稿。"""
    for L in range(min(n, len(ctx) - 1), 0, -1):
        suf = ctx[-L:]
        for i in range(len(ctx) - L - 1, -1, -1):
            if ctx[i:i + L] == suf:
                return ctx[i + L:i + L + gamma]
    return []
```

它在"输出抄输入"的任务上极准（摘要、文档问答、多轮对话、代码编辑——输出里大段引用输入），成本是一次字符串匹配。这是有生产实现的成熟技术：vLLM 里 `speculative_model="[ngram]"`、llama.cpp 的 n-gram speculator、HF transformers 的 `prompt_lookup_num_tokens`；同一思路的形式化版本是 REST（**arXiv:2311.08252**）。

本机实测（提示词 = 64 个 token 的片段重复两遍，共 128 token，生成 32 个 token）：

```text
基线（33 次目标前向）                              :  375.0 ms   1.00x
γ=2  PLD（目标前向 22，草稿前向 0，提出 30 个）    :  309.9 ms   1.21x   命中率 0.433  每轮产出 1.62
γ=4  PLD（目标前向 18，草稿前向 0，提出 39 个）    :  275.5 ms   1.36x   命中率 0.487  每轮产出 2.12
γ=8  PLD（目标前向 18，草稿前向 0，提出 63 个）    :  280.4 ms   1.34x   命中率 0.333  每轮产出 2.24
对照：随机提示词上 PLD γ=4                         : 命中率 0.067  每轮产出 1.14  墙钟 0.67x
```

**同一份代码、同一个目标模型，只是把草稿从"2 层小模型"换成"查表"，墙钟就从 0.55x 变成 1.36x**，而且这几组输出依然逐位一致。这就是公式里那个 c 的杠杆：0.255 → ≈0。

对照组也很说明问题：**随机提示词上 PLD 命中率掉到 0.067、墙钟 0.67x**。PLD 的适用面很窄——只在"输出抄输入"的任务上成立；查不到模板就退化成普通解码，白付一次前向的开销。别把 1.36x 当成通用加速比。

## 🎲 采样模式：无损不是形容词，是可以逐项验证的恒等式

前面都是贪心。真实产品要按温度采样，这时候"接受"变成一次拒绝采样（rejection sampling）：

- 草稿提议 x ~ q，以概率 `min(1, p(x)/q(x))` 接受；
- **被拒绝时，必须从残差分布 `norm(max(0, p − q))` 重抽，而不是原地重抽 q。**

正确性可以一行推完：`p_out = min(p,q) + max(p−q,0)·(1−α)/(1−α) = p`，逐项恒等。

那"拒绝后原地重抽 q"这种常见错实现会怎样？输出分布会变成 q 本身，偏差恰好是 `TV(q, p) = 1 − α`。蒙特卡洛（100 万次采样，8 个候选 token）验证如下：

```text
   ε     α=Σmin(p,q)  错误实现 TV=1-α  实测TV(错)  实测TV(对)   噪声 1/√N 参考
 0.00       1.000        0.0000        0.0008     0.0008        0.0009
 0.05       0.983        0.0170        0.0170     0.0009        0.0009
```

## 💻 一个可运行的完整核心（本机 45 秒跑完）

上面所有数字都出自 `05-speculative-decoding.py`，纯 numpy + 标准库。核心是两个函数（模型定义略，见前面 `body()` 的用法）：

```python
def greedy(model, ids, n_new, temp=1.0):          # 基线：一次前向一个 token
    ids = list(ids)
    logits, cache = model.forward(np.array(ids), None)
    for _ in range(n_new):
        tok = int(np.argmax(logits[-1] / temp))
        ids.append(tok)
        logits, cache = model.forward(np.array([tok]), cache)
    return ids


def spec(target, draft, ids, n_new, gamma, temp=1.0):
    """投机解码（贪心验证）。关键：logits 第 i 行预测的是第 i+1 个位置，
    所以「第 0 个待验证 token」要用上一轮留下的目标分布 t_next 来判。"""
    committed, out = list(ids), list(ids)
    t_logits, t_cache = target.forward(np.array(committed), None)
    t_next = t_logits[-1]                          # 目标模型对「下一位置」的分布
    d_logits, d_cache = draft.forward(np.array(committed), None)
    pending, st = None, {"rounds": 0, "t_fwd": 1, "d_fwd": 1, "hit": 0, "drafted": 0}
    while len(out) < len(committed) + n_new:
        base = len(out) - (1 if pending is not None else 0)
        batch, q_logits, off = [], [], 0
        if pending is not None:                    # 上一轮补出的 token 也要进验证批
            batch.append(pending)
            d_logits, d_cache = draft.forward(np.array([pending]), d_cache)
            st["d_fwd"] += 1
            off = 1
        for _ in range(gamma):                     # 草稿串行抢答 γ 个
            tok = int(np.argmax(d_logits[-1] / temp))
            batch.append(tok); q_logits.append(d_logits[-1])
            d_logits, d_cache = draft.forward(np.array([tok]), d_cache)
            st["d_fwd"] += 1
        v_logits, v_cache = target.forward(np.array(batch), t_cache)   # 目标一次判 γ+1 个
        st["t_fwd"] += 1; st["rounds"] += 1
        n_acc, rejected = 0, False
        for i in range(len(batch)):
            p = softmax(t_next if i == 0 else v_logits[i - 1], temp)
            hit = int(np.argmax(p)) == batch[i]
            if i >= off:
                st["drafted"] += 1
                st["hit"] += int(hit)              # EAGLE 口径：每个位置独立统计
            if not rejected:                       # n_acc 只数到第一个不匹配为止
                if hit:
                    n_acc += 1
                else:
                    rejected = True
        if n_acc > 0:                              # 上下文前进了，t_next 才更新
            t_next = v_logits[n_acc - 1]
        nxt = int(np.argmax(t_next / temp))        # 拒绝则从目标分布重取（贪心=argmax）
        keep = base + n_acc
        t_cache, d_cache = trunc(v_cache, keep), trunc(d_cache, keep)
        out = out[:base] + list(batch[:n_acc]) + [nxt]
        pending = nxt
    st["wall"] = ...                               # 统计与计时
    return out, st
```

调试时踩到的两个坑，都写在这里免得你重踩：

1. **logits 的行号是"预测下一个位置"，不是"当前位置"。** 我第一版用本轮前向的第 0 行去判第 0 个草稿 token，结果第一枚草稿永远被判错（因为那一行预测的是再往后一个位置）。正确做法是把上一轮的目标分布 `t_next` 带过来——这也是真实实现里"每次验证批都要把上一轮补出的 token 放进第一位"的原因。
2. **"逐位一致"这个测试在 float32 下是不可判定的。** 批量矩阵乘和逐步矩阵乘的舍入路径不同，同一位置 logits 会差 ~2e-06，足以在近似打平的位置翻转 argmax，导致验证结果与基线偶发不一致（我实测到过）。换成 float64 后差值降到 ~3e-15，测试才稳定。

## 💡 什么时候该用、什么时候别用

| 场景 | 判断 |
|---|---|
| 低并发 + 长输出 + 有对齐好的草稿 | ✅ 最甜的点，1.5x-4x |
| 输出大段抄输入（摘要/RAG/代码编辑） | ✅ 上 PLD，c≈0，但只在这类任务上 |
| 有 MTP/内置草稿头的模型（如 DeepSeek-V3 的 MTP） | ✅ 草稿在模型内部，省掉一个模型和一份显存 |
| 高并发、大 batch 服务 | ❌ batch 已经把解码阶段喂成算力受限，算力没富余可买 |
| 显存紧张 | ❌ 草稿权重 + 草稿自己的 KV cache 都要显存，可能挤掉并发度 |
| 短输出（几十个 token） | ❌ 预热和验证的固定开销吃不回来 |
| 采样模式但拒绝后重抽草稿 | ❌ 输出分布已经不是目标模型了（TV = 1−α） |

还有两个容易忽略的点：**温度**不影响贪心模式下的 argmax 命中率（只影响采样模式下的分布形状），所以"调低温度提高接受率"这种说法要分清模式；**上下文不匹配的草稿会退化**——跨领域的草稿模型可能比没有草稿更慢（反例 1 的 0.29x 就是这个）。

## 📌 小结

一句话：**投机解码把"K 次串行前向"换成"1 次并行验证 + K 次廉价草稿"，它买的是串行步数，付的是多余的算力。**

- 收益公式：`E[接受数] = (1-α^(γ+1))/(1-α)`，`加速比 = E[接受数]/(1+γc)`。α 决定上限，c 决定最优 γ，c=1 时永远是 1.00x。
- 无损性有两条腿：贪心模式下接受的是目标自己的 argmax；采样模式下拒绝时必须从残差分布 `norm(max(0,p−q))` 重抽，此时输出分布与目标逐项相等（实测 TV 恒等于采样噪声）。
- 真正的门槛是**草稿对齐**：本机玩具上未对齐的截断草稿 argmax 一致率 0.046，蒸馏对齐后 0.550——这就是同一篇 EAGLE-2 里 1.50x 和 3.05x 的差别来源。
- 而这笔账能不能变现，看的是硬件的瓶颈在带宽还是算力：同一个算法、同一个 α，GPU 上 2x-3x，我的 CPU 玩具上 0.44x-0.68x，换成查表草稿才回到 1.39x。

下一篇打算写 logits 采样（top-k / top-p / 频率惩罚）——温度那一期只讲了"怎么把分布变形"，还没讲清"从变形后的分布里怎么挑一个 token"。
