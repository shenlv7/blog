> 一段 212 个字的中文，cl100k_base 收 **288 个 token**，o200k_base 收 **212 个**。
> 同样内容的 135 个英文词，两代词表都收 161 / 162 个——差一个，基本算没动。
> 中文的账单砍掉四分之一，英文的账单原地不动。这不是模型变强了，是税则改了。

**读这篇要会**：BPE 是按频率合并相邻符号的压缩算法／模型看到的输入是 token id 不是字符／上下文窗口的上限按 token 计。不需要读过分词器源码。

## 🎯 一个汉字为什么会被收两次钱

做过中文产品的都遇到过这种对不上账的事：同样一份知识库，同事估「100 万字大概 130 万 token」，你算出来 180 万。差的那部分不在长度上，在**分词器把中文切得多碎**上。

模型不认识汉字，只认识词表里的编号。词表是一个固定预算：cl100k_base 约 10 万条，o200k_base 约 20 万条。BPE（Byte Pair Encoding）的起点永远是 256 个字节符号，之后每一次合并都在花这笔预算。中文的先验成本比英文贵在第一步：一个汉字在 UTF-8 里占 **3 个字节**，一个英文字母只占 1 个。也就是说，在还没开始合并之前，同样一句话的中文符号序列长度就是英文的三倍左右。

英文的高频词有机会整词被合并成一条（` the`、`tion`、` training`），一条就能顶 4 到 8 个字符；中文的高频双字词（"训练"、"梯度"）要靠合并两次才成形，而它们在中英混合语料里的出现频率被 3 倍字节数稀释过——同样的字符数，中文占用的语料窗口面积更小，统计上就是「更罕见」。预算有限时，合并顺序先照顾英文，中文剩下单字。

## 🔬 机制：半个汉字的 token 真的存在

把一句话按 token 切开，看每个 token 单独解码出来是什么：

```
分布式训练的梯度累积需要按 token 数加权，否则长序列会被系统性低估。

cl100k_base    38 tok: 分 | 布 | 式 | � | � | � | � | 的 | � | � | � | 度 | � | ...
o200k_base     26 tok: 分 | 布 | 式 | 训练 | 的 | 梯 | 度 | 累 | 积 | 需要 | 按 | ...
```

`�` 不是打印错误，是**半个 UTF-8 序列**。cl100k 里「训」这个字被切成 2 字节 + 1 字节两条 token，任何一条单独 decode 都凑不出合法字符，只能显示成替换符。这条细节有两个直接后果：

1. **按 token id 切片再拼回字符串会出乱码**。想按窗口截断长文本，必须走 `decode`（它会做字节级拼接），或者干脆按字符切。按 token 边界切字节是最常见的静默 bug。
2. **它是 token/字 大于 1 的唯一来源**。逐字符统计（token 跨字时两边各记一次）：

| 词表 | 只要 1 个 token | 要 2 个 | 要 3 个 | 统计字符数 |
|---|---|---|---|---|
| cl100k_base | 82% | 15% | 3% | 265 |
| o200k_base | 98% | 2% | 0% | 265 |

cl100k 里有 18% 的字符被切开，o200k 只剩 2%。所谓「中文贵」，大头就是这 18%。

## 🏗️ 成本模型：把字数换成 token

设 $f$ 为 token/字 的膨胀系数，$N$ 为汉字数，$W$ 为上下文窗口的 token 上限：

$$\text{tokens} = N \times f \qquad N^{\max} = \frac{W}{f}$$

代本机实测值：$f_{\text{cl100k}} = 1.358$，$f_{\text{o200k}} = 1.000$。一个标称 128k 的窗口，装得下 **9.4 万汉字** 还是 **12.8 万汉字**，取决于里面用的是哪代词表——差 3.4 万个字，一本中篇小说的量。100 万 token 的预算同理：73.6 万汉字 对 100.0 万汉字。

这个系数的麻烦之处在于它会**越过 API 边界**往下传：embedding 的输入上限、chunk 的切分大小、RAG 的召回条数、微调样本的 max_len，全都是 token 单位。用「字数 ÷ 1.5」当经验值，在 o200k 上会高估，在 cl100k 上会低估，两边都留不出安全余量。要么按词表实测系数，要么在 pipeline 里真调一次分词器。

## 💻 实测：4 段平行语料，两代词表

方法：写 4 段内容等价的中英对照（推理瓶颈、UTF-8 底账、词表取舍、口语版），用 `tiktoken` 的两套公开词表分别计数。语料规模小（212 字 / 135 词），结论是方向性的，不是全语料统计。

```python
import tiktoken

SEGMENTS = [
    ("推理瓶颈",
     "注意力机制在推理阶段的主要瓶颈不是浮点运算，而是显存带宽：每生成一个 token，都要把整个 KV cache 读一遍。批处理能摊薄权重读取，却摊薄不了每个序列各自的缓存。",
     "At inference time the bottleneck of attention is not floating-point arithmetic but memory bandwidth: ..."),
    # 其余 3 段同构，完整脚本见仓库
]

ENCS = {n: tiktoken.get_encoding(n) for n in ("cl100k_base", "o200k_base")}

for name, zh, en in SEGMENTS:
    for k, enc in ENCS.items():
        print(name, k, len(enc.encode(zh)), len(enc.encode(en)))
```

真实输出（完整见文末脚本）：

```
段落        汉字  英文词  cl100k中 cl100k英  o200k中 o200k英
推理瓶颈      64    35       90      44       62      45
UTF-8 底账    66    40       77      47       60      47
词表的取舍     42    27       65      31       50      31
口语版        40    33       56      39       40      39

cl100k_base   中文 288 tok / 212 字 = 1.358 tok/字 | 英文 161 tok / 135 词 = 1.193 tok/词 | 中/英 = 1.79x
o200k_base    中文 212 tok / 212 字 = 1.000 tok/字 | 英文 162 tok / 135 词 = 1.200 tok/词 | 中/英 = 1.31x
```

两件事值得单独拎出来：

- **中文降 26.3%，英文涨 0.6%**。词表从 10 万扩到 20 万，新增的预算几乎全部花在非英文上。英文的 1.19 → 1.20 是噪声，不是退化。
- **1.000 是这 212 个字上的巧合**。四段加起来 212 token / 212 字符，恰好一一对应，不代表 o200k 在所有中文上都严格 1 token/字——同一句话里仍有 2% 的字符被切开。不要把这个数当常数写进代码。

## 💡 能拿去用的三条

**选词表就是选税则，且这个税只对一种语言收。** 中文为主的产品，用中文语料占比高的词表（o200k 这一类扩容词表，或中文模型自带的词表），省下来的不是几个百分点，而是四分之一的 token 预算和三分之一的窗口容量。反过来，如果你的 pipeline 里所有阈值都是按 cl100k 的 1.36 tok/字 标定的，换词表之后要重标一遍，别只换 API。

**别按 token 边界切字符串。** 有 18% 的字符在 cl100k 里横跨两条 token，切在中间就是半个 UTF-8 序列。分块、摘要、截断一律走字符边界或 `decode` 之后再切。

**预算表要写成「token/字 × 字数」的形式，系数逐词表实测。** 这条经验值会随词表版本变，写死一个数字（不管 1.3 还是 1.0）都会在某个版本上悄悄错 30%。

本次只测了 OpenAI 两代公开词表，中文厂商模型的词表没有实测，不给数字——但机制相同：谁的语料里中文占比高，谁的合并顺序就先照顾中文。
